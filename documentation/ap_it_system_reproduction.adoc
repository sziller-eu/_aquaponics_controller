== IT System Reproduction

=== Purpose

This document defines how to recreate the production Aquaponics controller from replacement hardware.

The target requirement is:

[IMPORTANT]
====
Given suitable replacement hardware, local installation media, project release artifacts, configuration backup, and persistent-data backup, an administrator shall be able to reconstruct a functioning Aquaponics controller without
undocumented knowledge.
====

=== User Accounts

Document all required local accounts.

The Engine shall run under a dedicated service account, separate from the API service account (see below).

Example structure:

[source,text]
----
Administrative user:       TBD
Engine service user:       aquaponics (system user and group, no login shell, no home directory;
                           created by systemd-sysusers from deploy/sysusers.d/aquaponics.conf)
API service user:          separate from the Engine service user / TBD
----

The `aquaponics` account owns the Engine's runtime and state directories and nothing else.
It belongs to no additional groups and has no device access (Issue #9).
Administrators use `root` (`sudo`) or `sudo -u aquaponics` for the administrative IPC; an administrative group is not defined yet.
Keep the account while `/var/lib/aquaponics/` exists, so that the lifecycle audit records keep their owner.

The Engine service user shall not have unrestricted privileges unless specifically required.

The Engine and the API shall run under separate service accounts. Document the groups and permissions of each account independently. The API account shall be restricted to the capabilities required by its intended operations and shall not receive hardware privileges merely because the Engine requires them.

=== Database Restore

Document an explicit restore process.

The procedure shall specify:

* which service is stopped;
* backup selected;
* backup validation;
* replacement method;
* ownership/permissions;
* command-journal reconciliation;
* restart;
* post-restore validation.

[IMPORTANT]
====
Restoring an older database backup may restore command records whose real-world effects occurred after that backup was created.

Pending or incomplete commands from a restored backup shall therefore not be replayed blindly. Physical state, current time, command identity, and command recovery semantics shall be reconciled before normal actuator execution resumes.
====

=== Production Service Topology

The production controller shall run at least two logically separate services:

[source,text]
----
aquaponics-engine.service
aquaponics-api.service
----

The Engine is the primary autonomous service.

The API is an external-interface service.

Failure of the API service shall not terminate or suspend physical control by the Engine.

=== Engine Service

Record:

[source,text]
----
Service name:       aquaponics-engine.service (Type=notify)
Unit path:          /etc/systemd/system/aquaponics-engine.service
                    (source: deploy/systemd/aquaponics-engine.service)
Service user:       aquaponics:aquaponics
Executable:         /opt/aquaponics/venv/bin/aquaponics-engine

                    --audit-file /var/lib/aquaponics/lifecycle_audit.jsonl
                    --cycle-interval 1.0

                    (absolute path: sudo's secure_path does not include the virtual environment)
Installed from:     wheel built by the ordinary user from commit TBD (record the commit hash)
Restart policy:     Restart=on-failure, RestartSec=5s, RestartPreventExitStatus=2 3 4,

=== Service Startup Order

The deployment shall document service dependencies.

Conceptually:

[source,text]
----
Linux / systemd
      |
      +--> aquaponics-engine.service
      |          |
      |          +--> autonomous physical operation
      |
      +--> aquaponics-api.service
                 |
                 | local IPC
                 v
              Engine

external clients --> API
----

The Engine service shall not depend on the API service.

API startup failure shall not prevent Engine startup or autonomous physical operation.

The API may start before or after Engine readiness, but it shall handle temporary Engine unavailability and recover communication when the Engine becomes available.

=== Logging

Document:

* journal configuration;
* persistent journal status;
* application log location if separate;
* rotation;
* retention;
* disk limits.

Logging must remain available after ordinary reboot where practical.

The Engine writes its diagnostic logs to standard error and does not bound what is kept there; under `systemd`, retention and persistence are those of the journal configuration recorded here.
Under the service, the lines are tagged `aquaponics-engine` and carry their syslog priority, so `journalctl -u aquaponics-engine -p err` selects failures.

To keep the journal across reboots (record the values used):

[source,text]
----
/etc/systemd/journald.conf:   Storage=persistent      (or create /var/log/journal)
                              SystemMaxUse=TBD
Persistent journal:           yes / no / TBD
----

Then `sudo systemctl restart systemd-journald`.
The optional Engine log file (`--log-file`) is bounded by the Engine itself (see "Diagnostic Logging (Initial Implementation)" in the Development and Operations chapter).

=== Startup Verification

After installation or replacement hardware boot, verify:

. Linux boot completes.
. No interactive login is required for Engine startup.
. Required filesystems mount.
. systemd starts the Engine without requiring API availability.
. Configuration validates.
. Local DB opens.
. Durable command state can be read.
. Hardware interfaces initialize.
. Required sensors are detected.
. Outputs enter known states.
. Incomplete prior operations and commands are reconciled according to recovery policy.
. Engine heartbeat becomes healthy.
. API service starts independently and can reach the Engine through the configured IPC mechanism.
. Local frontend becomes available if installed.
. Core operation works without Internet access.

=== Shutdown Verification

Verify clean shutdown behaviour.

The Engine should:

* stop accepting or initiating new state-changing work;
* preserve already accepted command state durably;
* leave incomplete operations in a recoverable state;
* persist critical state;
* close DB connections;
* leave hardware in defined states where required;
* terminate within configured limits.

=== Reboot Verification

Perform a complete unattended reboot test.

Confirm:

* automatic OS boot;
* automatic Engine start without API dependency;
* successful persistent-state and command-journal reconciliation;
* correct sensor discovery;
* correct actuator initialization;
* healthy control loop;
* API recovery/reconnection where the API is installed.

=== Network-Loss Verification

Disconnect the LAN.

Confirm that core physical control continues.

Expected unavailable functions may include:

* remote UI;
* remote mobile access;
* SHMC;
* e-mail.

Expected remaining functions include:

* Engine;
* schedules;
* sensors;
* actuators;
* local DB;
* local Engine/API IPC;
* local API service where installed, although remote clients cannot reach it over the disconnected LAN.

=== Process-Failure Verification

Terminate the Engine process in a controlled test.

Confirm:

* systemd detects termination;
* restart policy activates;
* persistent and physical state are reconciled;
* accepted incomplete commands are reconciled without silent loss or blind duplication;
* Engine returns to healthy operation;
* API communication recovers where applicable;
* failure remains visible in diagnostics.

=== Sensor-Failure Verification

Disconnect or disable each important sensor in a controlled test.

Verify that the Engine:

* identifies invalid/missing measurement;
* does not convert failure into plausible data;
* enters the documented fallback behaviour;
* raises the appropriate alarm.

=== Database-Failure Verification

In a non-production test environment:

* test invalid DB;
* test schema mismatch;
* test restore;
* test interrupted migration where applicable;
* verify that a state-changing request is not reported as durably accepted when command persistence fails.

The production biological system must not be endangered during destructive testing.

=== Storage-Full Verification

In a controlled test environment, verify behaviour when storage availability becomes critically low.

The Engine should detect the condition before uncontrolled failure where possible.

If storage exhaustion prevents durable command persistence, new state-changing requests shall not be falsely reported as accepted.

=== Power-Recovery Verification

Test power-loss recovery using safe methodology.

Verify:

* filesystem integrity;
* DB integrity;
* automatic boot;
* automatic service start;
* startup reconciliation;
* control recovery.

=== UPS Verification

If a UPS is installed, verify:

* outage detection;
* controller behaviour on outage;
* controlled shutdown;
* restart when power returns;
* protection against rapid power cycling where supported.

=== Release Rollback

Document the procedure for returning to the previous known-good application release.

Rollback procedure shall not assume that database migrations are automatically reversible.

Rollback shall also verify that the selected application version can correctly interpret the installed command-journal and operational-state schema.

=== Disaster Recovery

A complete disaster scenario shall assume:

[source,text]
----
Raspberry and primary storage are lost.
----

Recovery should require:

* replacement controller;
* replacement storage;
* release bundle;
* configuration backup;
* secrets;
* database backup;
* hardware documentation.

After restoration, physical state and restored command state shall be reconciled before ordinary actuator execution resumes.

The target is reproducible reconstruction rather than preservation of one irreplaceable machine image.
