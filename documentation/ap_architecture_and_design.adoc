== Architecture and Fundamental Design

=== Architectural Objective

The Aquaponics architecture shall provide a robust autonomous controller for a real physical installation.

The target structure is conceptually:

[source,text]
----
                  OPTIONAL EXTERNAL SYSTEMS

      Browser      Mobile      Human      AI      SHMC
          \           |          |        |        /
           \          |          |        |       /
            +---------+----------+--------+------+
                              |
                             API
                              |
                              v
                    AQUAPONICS ENGINE
                              |
                  authoritative decisions
                              |
                    hardware abstraction
                              |
              +---------------+---------------+
              |               |               |
           sensors         actuators       optional
                                           media
              |               |
              +------- physical system -------+
----

=== Engine Authority

The Engine shall be the authoritative software controller of the physical installation.

Its operation shall not be request-driven.

API calls may influence an already-running system, but the absence of API calls shall not stop:

* schedules;
* pump control;
* aeration;
* sensor acquisition;
* alarms;
* local persistence;
* recovery logic;
* normal autonomous operation.

=== Autonomous Control Loop

The normal decision flow shall conceptually follow:

[source,text]
----
Sensors
   |
   v
Observations
   |
   v
Validated System State
   |
   v
Control Policies
   |
   v
Decision
   |
   v
Desired Actuator State
   |
   v
Hardware Adapter
   |
   v
Physical System
----

=== Central Decision Authority

Normal coordinated decisions shall be made by one authoritative control layer.

This prevents multiple independent controllers from unintentionally producing:

* oscillation;
* hunting;
* unstable feedback;
* conflicting actuator commands;
* contradictory state.

Individual hardware devices shall not independently determine high-level aquaponics behaviour unless they implement an explicitly designated safety function.

=== Unified Command Execution Architecture

All state-changing actions shall pass through one authoritative Engine-owned command path.

This applies regardless of where the requested action originated.

Possible command origins include:

* autonomous Engine control policies;
* schedules;
* API requests;
* local administrative CLI requests;
* SHMC;
* authorized AI agents;
* authorized human operators.

No origin shall receive a privileged shortcut directly to physical hardware.

Conceptually:

[source,text]
----
                  EXTERNAL ORIGIN
        API / CLI / SHMC / AI / Human
                         |
                         | submit intent
                         v
                  ENGINE INGRESS
                         |
                         | validate / accept
                         v
                DURABLE COMMAND JOURNAL
                         |
                         |
                         +<----- scheduled actions
                         |
                         +<----- autonomous actions
                         |
                         v
                  COMMAND EXECUTOR
                         |
                         v
                  control validation
                         |
                         v
                 hardware adapters
                         |
                         v
                  physical system
----

[IMPORTANT]
====
The Engine shall have one authoritative state-changing execution path.

An external API command, a scheduled operation, and an autonomous control decision shall ultimately pass through the same command execution mechanism before affecting physical hardware.
====

=== Engine Ingress

The Engine shall expose an explicit ingress boundary for state-changing external intentions.

External components shall submit an intent to the Engine.

Examples include:

[source,text]
----
turn light 1 ON
activate aeration for 30 minutes
apply temporary pump override
change an authorized operating parameter
----

The ingress boundary is responsible for accepting an external intention into the Engine's authority.

Transport reception alone does not mean that a command has been accepted.

A state-changing request shall only be considered accepted when the Engine has:

* received it;
* validated its basic structure;
* determined that it may enter the Engine command system;
* persisted the resulting command durably.

If the Engine cannot durably accept the command, the caller shall not receive a false success acknowledgement.

=== Transport Is Not Command Semantics

The mechanism used to carry an external request into the Engine is an implementation detail.

Possible local transports may include:

* Unix domain socket;
* localhost TCP;
* another explicitly selected local IPC mechanism.

The transport shall not define the Engine's control semantics.

Conceptually:

[source,text]
----
API
 |
 | local IPC
 v
Engine ingress
 |
 | Engine semantics begin here
 v
Durable command journal
----

Changing IPC technology shall not require changing:

* control policies;
* command semantics;
* actuator semantics;
* persistence semantics;
* scheduling semantics.

=== Engine Ownership of Persistence

The Engine shall be the sole authoritative owner of its operational persistence.

External components shall not directly insert, update, or delete operational records in order to control the system.

In particular:

[source,text]
----
NOT ALLOWED

API
 |
 v
commands table
 |
 v
Engine
----

The intended architecture is:

[source,text]
----
API
 |
 | submit intent
 v
Engine ingress
 |
 | Engine persists accepted command
 v
command journal
 |
 v
Engine command execution
----

This preserves Engine sovereignty over:

* command validation;
* persistence;
* ordering;
* execution;
* recovery;
* auditability.

=== Durable Command Journal

Accepted state-changing commands shall be recorded durably before normal physical execution.

The durable command journal exists so that accepted work can survive:

* Engine restart;
* process crash;
* operating-system restart;
* temporary interruption of execution.

A command record should contain enough information to identify at least conceptually:

* command identity;
* origin;
* command type;
* parameters;
* creation/acceptance time;
* intended execution time where relevant;
* current execution state;
* execution/result relationship.

Exact database schema belongs to implementation documentation.

Command history shall remain auditable.

Implementation may use append-only execution records or another mechanism that preserves equivalent historical traceability.

=== Command Lifecycle

A command shall have an explicit lifecycle.

A minimal conceptual lifecycle is:

[source,text]
----
QUEUED
   |
   v
EXECUTING
   |
   +--------> FAILED
   |
   v
DONE
----

More detailed state-machine semantics may be introduced where required.

The Engine shall be able to determine after restart whether a command is:

* waiting;
* being recovered;
* complete;
* failed;
* ambiguous and requiring reconciliation.

A state-changing command must not disappear merely because the Engine process restarted after accepting it.

=== Command Idempotency

Commands that may be observed or retried across process or network failure shall have deliberate idempotency semantics.

The Engine shall avoid executing one logical operation multiple times merely because:

* the API retried;
* a connection was interrupted;
* the Engine restarted;
* a loop iteration was delayed.

Where needed, commands shall use an explicit command identifier, occurrence identifier, or idempotency key.

=== Command Ordering and Execution Fairness

When multiple commands are eligible for execution, their ordering shall be deterministic.

The Engine shall not depend on accidental properties such as:

* database row order;
* thread scheduling;
* socket arrival timing;
* Python object ordering.

The command model shall support an explicit ordering mechanism using appropriate information such as:

* priority;
* intended execution time;
* acceptance sequence;
* command identity.

The exact priority policy shall be defined with the corresponding control semantics.

Command processing shall also be bounded so that a large command backlog cannot indefinitely starve:

* sensor acquisition;
* state reconciliation;
* safety evaluation;
* scheduling;
* health monitoring.

Explicit safety mechanisms may receive higher priority than ordinary commands.

Manual overrides and other control modes shall be incorporated into control-state evaluation so that autonomous policies do not continuously generate commands contradicting an active authorized override.

=== Engine Outer Loop

The production Engine shall run continuously.

Its outer loop shall repeatedly provide opportunities for:

* sensor acquisition;
* state reconciliation;
* external-intent ingestion;
* schedule processing;
* autonomous-policy evaluation;
* command execution;
* persistence;
* health reporting.

Conceptually:

[source,python]
----
while running:

    acquire_observations()

    reconcile_state()

    accept_available_external_intents()

    materialize_due_scheduled_commands()

    evaluate_autonomous_control()

    execute_due_commands()

    persist_required_state()

    update_health_heartbeat()

    wait_for_next_cycle()
----

This is conceptual pseudocode.

The exact ordering and decomposition may change where technically justified.

The invariant is that external communication is processed as part of the continuously operating Engine rather than replacing or driving the Engine loop.

Most cycles may contain no external instruction.

In that case, external-intent handling is effectively a non-action step and autonomous operation continues normally.

=== Bounded External Ingress

Processing external communication shall never block the autonomous control loop indefinitely.

The Engine ingress mechanism shall therefore be non-blocking or explicitly time-bounded. An unavailable, stalled, malformed, or overloaded external client shall not prevent:

* sensor acquisition;
* schedule processing;
* autonomous decisions;
* command execution;
* health-heartbeat updates.

Each Engine cycle may process a bounded number of newly arrived external intents or spend a bounded amount of time on ingress processing.

Additional requests may remain queued for later processing.

[IMPORTANT]
====
External communication is serviced by the Engine. +
External communication shall never become the clock that drives the Engine.
====

The Engine may also service pending external requests while it idles between operating cycles, so that the responsiveness of a request does not depend on the cycle interval.
This does not add a second loop or a thread, and it does not start an additional operating cycle: the cycle deadline is unchanged, and the idle servicing is bounded in the same way as servicing within a cycle.
A request that arrives while an operating cycle is in progress waits for the end of that cycle.
Each phase of the control loop shall therefore be time-bounded, so that a long-running phase cannot delay external communication indefinitely (see "Operating-Cycle Phases").

=== Operating-Cycle Phases

The terms "control cycle" and "operating cycle" denote the same thing: one pass of the Engine through its outer loop.
The code uses "operating cycle" (`Engine.run_operating_cycle`).

One operating cycle passes through the following phases, in this order:

[cols="1,3,3",options="header"]
|===
|Phase |Responsibility |Current implementation

|`ACQUIRE_OBSERVATIONS`
|Read sensors and validate the readings as observations.
|Placeholder. Reads nothing.

|`RECONCILE_STATE`
|Derive the validated system state from observations and known actuator state.
|Placeholder. Keeps no state.

|`INGEST_EXTERNAL_INTENTS`
|Service pending external requests within the ingress bounds (see "Bounded External Ingress").
|Services pending local administrative IPC requests.

|`EVALUATE_SCHEDULED_WORK`
|Materialize due scheduled occurrences as commands (see "Scheduled Actions Use the Command Path").
|Placeholder. Creates nothing.

|`EVALUATE_CONTROL_POLICIES`
|Evaluate autonomous control policies and produce action intents (see "Autonomous Actions Use the Command Path").
|Placeholder. Decides nothing.

|`EXECUTE_READY_COMMANDS`
|Execute ready commands, exclusively through the durable command journal and the unified command path.
|Placeholder. Executes nothing and accesses no hardware.

|`FINALIZE_CYCLE`
|Persist required cycle state and refresh the health heartbeat (see "Meaningful Health Heartbeat").
|Placeholder. Persists nothing.
|===

This order follows "Engine Outer Loop".
A cycle counts as completed only when all of its phases have finished.
A placeholder phase does nothing and shall not be described as performing the responsibility it is reserved for.

Phase time limits::
Every phase has a declared time limit.
The limits are cooperative budgets, not pre-emptive deadlines: the Engine executes in one thread and cannot interrupt a running phase.
A phase shall not start further work once its budget is used up, and every operation within a phase shall bound its own duration.
The Engine measures the duration of each phase with the monotonic clock (see "Time Handling") and reports a phase that exceeded its limit as a diagnostic warning.
An overrun does not stop the Engine.
A phase that blocks indefinitely cannot be detected reliably by the thread executing it; detecting that is the responsibility of external supervision and the watchdog (see "Process Supervision", "Meaningful Health Heartbeat" and "Hardware Watchdog").
The sum of the phase limits bounds the time a request waits for a cycle in progress, and shall remain well below the timeout used by local clients.

Cycle scheduling::
Each cycle is due one cycle interval after the start of the previous cycle, measured with the monotonic clock.
A cycle that takes longer than the interval is followed immediately by the next cycle; missed cycles are not caught up.

Phase failure::
An unexpected exception in a phase ends the cycle at that phase: the remaining phases do not run and the cycle is not counted.
In the current implementation, the Engine then follows its failure path: the failure, with the phase and the cycle number, is recorded in the lifecycle audit history, the Engine shuts down and the process exits with a failure status.
There is as yet no retry, phase-level recovery or degraded mode (see "Degraded Operation" and "Fault Monitoring, Retry, and Escalation").

Stop requests::
A controlled-shutdown request, or a handled termination signal, does not interrupt a cycle in progress.
The cycle completes its remaining phases, each of which is bounded, and no further cycle starts.
Before physical command execution is introduced, this behaviour shall be reviewed to ensure that no unsafe new physical operation is started after a shutdown has been requested.

Idle servicing::
Requests serviced while the Engine idles between cycles (see "Bounded External Ingress") are not part of any phase.
Idle servicing runs no phase and starts no cycle.

=== Autonomous Actions Use the Command Path

Autonomous policy evaluation shall not create a second actuator-control path.

For example, avoid:

[source,text]
----
temperature policy
      |
      v
pump.turn_on()
----

when externally requested operations use a command system.

Instead:

[source,text]
----
temperature policy
      |
      v
autonomous action intent
      |
      v
durable command
      |
      v
normal command executor
      |
      v
pump
----

This ensures that autonomous actions receive the same:

* validation;
* persistence;
* execution semantics;
* history;
* recovery behaviour;

as other state-changing actions.

=== Scheduled Actions Use the Command Path

Schedules shall materialize due operations into ordinary Engine commands.

A scheduler shall not bypass the command mechanism and operate physical hardware directly.

Conceptually:

[source,text]
----
Schedule
   |
   | occurrence becomes due
   v
Command materialized
   |
   v
Durable command journal
   |
   v
Normal command execution
----

A scheduled occurrence should be identifiable by its intended absolute occurrence time or equivalent stable occurrence identity.

This shall prevent duplicate execution caused by:

* delayed loop iterations;
* restart;
* midnight/date transitions;
* repeated schedule evaluation.

=== Query Path

Read-only queries are distinct from state-changing commands.

Examples include:

* current temperature;
* current logical pump state;
* active alarms;
* Engine health;
* historical measurements;
* command status.

These operations normally do not need to become commands.

They shall use an Engine-owned query/read interface.

Conceptually:

[source,text]
----
API / CLI / SHMC
        |
        | query
        v
Engine Query Interface
        |
        v
Current State / History
----

External clients shall still not directly use the operational database as their normal query interface.

This keeps persistence layout private to the Engine and allows the Engine to expose stable domain semantics.

=== Active Read Operations

A request for already-known state is a query.

A request that causes new physical activity is an action.

For example:

[source,text]
----
"Return the latest known water temperature"
    -> query
----

while:

[source,text]
----
"Read the physical temperature sensor immediately"
    -> active operation
    -> command path
----

The distinction shall be based on whether the operation causes new physical or state-changing work.

=== Lifecycle-Control Requests

A request asking the Engine to change the state of its own process lifecycle is distinct from an operational command.

An operational command requests a change to physical or logical operating state, for example controlled equipment, an override, an operating parameter, or a schedule.
Operational commands follow the "Unified Command Execution Architecture" and the "Durable Command Journal".

A lifecycle-control request asks the Engine process itself to change its lifecycle.
The first lifecycle-control request is the operator request for a controlled Engine shutdown ("STOP").

An authorized operator STOP request is a lifecycle-control request, not a durable operational command.
Consequently:

* the Engine processes the request;
* the request is subject to Linux authorization (see "Local Administrative Access") and to Engine validation;
* the request does not require the durable command journal;
* the request is not replayable;
* a previous STOP request shall never be re-executed automatically after a restart;
* the request is recorded as historical evidence in the lifecycle audit history (see "Engine Lifecycle Audit History"), which is never interpreted as pending work.

This classification creates no general exception to the durable command requirements.
Every request to change physical or logical operating state remains an operational command.

A lifecycle-control request does not itself operate hardware.
The shutdown procedure it initiates shall continue to respect all applicable safety and physical command-execution requirements, including the equipment-specific failure policy (see "Equipment-Specific Failure Policy" and "Clean Shutdown").

Operating-system signals such as SIGINT and SIGTERM are not lifecycle-control requests.
The Engine may respond to them with a best-effort controlled shutdown.
A handled signal does not establish that the interruption was authorized by an operator.
That distinction shall remain explicit for process supervision (see "Process Supervision").

Other lifecycle requests, such as a restart request or entering maintenance mode, are not classified here.
Each shall be classified explicitly when it is introduced.

=== Request Classes

Every request that reaches the Engine through a client interface belongs to exactly one class.
The Engine distinguishes them explicitly when it dispatches a request.

[cols="2,4,3",options="header"]
|===
|Class |Meaning |Persistence and replay

|Query
|A read-only request for information the Engine already has (see "Query Path").
It changes no physical or logical operating state.
|No durable command journal. Nothing about the request is persisted, and it is never replayed after a restart.
Its result is not "accepted work".

|Operational command
|A request to change physical or logical operating state (see "Unified Command Execution Architecture").
|Requires the "Durable Command Journal". Acceptance is durable.

|Lifecycle-control request
|A request that the Engine process change its own lifecycle (see "Lifecycle-Control Requests"). The first one is STOP.
|Not journaled as an operational command and never replayed. Recorded as evidence in the lifecycle audit history.
|===

The first queries are two stateless diagnostics for proving the communication path.
`ping` returns Engine-generated runtime information (the execution identifier, the process identifier, the number of completed operating cycles and the Engine's current UTC time).
`echo` returns the text it was given, after Engine-side validation.
Neither operates hardware or changes any state.
They are not added to the lifecycle audit history, which records lifecycle evidence only.

A request correlation identifier lets a client match an answer to its request and lets diagnostic traces name a request without quoting its content.
It is not a durable command identifier and not an idempotency key.
A query answer is never described as "accepted": that word is reserved for durable acceptance of an operational command (see "Durable Command Journal").

Authorization applies to every class.
Linux access control lets a client connect (see "Local Administrative Access"), and the Engine independently validates each request, whatever its class.

=== API Process Separation

The API shall run as a process separate from the autonomous Engine.

Conceptually:

[source,text]
----
Web / Mobile / SHMC / AI / other clients
                  |
                  v
       aquaponics-api.service
                  |
                  | local IPC
                  v
      aquaponics-engine.service
                  |
                  v
        physical control system
----

Failure, restart, upgrade, or temporary unavailability of the API process shall not terminate the Engine's physical control loop.

The Engine shall not depend on the API process for:

* scheduling;
* sensor acquisition;
* autonomous control;
* actuator execution;
* local persistence;
* recovery.

=== API Command Semantics

For state-changing requests, the API acts as an authenticated and authorized transport adapter.

It shall:

* authenticate the caller;
* authorize the requested capability;
* validate request syntax;
* submit the resulting intent to the Engine;
* return the Engine's acceptance or rejection result.

The API shall not:

* execute the actuator itself;
* persist commands directly into the Engine database;
* bypass the Engine command journal.

A successfully accepted state-changing request should return a command identifier or equivalent execution reference.

Clients may then query the resulting command state.

Whether an API call optionally waits for completion is a presentation concern.

Waiting shall never bypass the durable command path.

=== CLI Command Semantics

Normal administrative CLI commands shall communicate with the running Engine through the supported Engine interface.

Examples include:

* status;
* health;
* alarms;
* inspect state;
* request override;
* release override.

The normal CLI shall not manipulate GPIO directly while the Engine is operating.

Direct low-level hardware diagnostics require an explicit maintenance condition.

Possible maintenance rules include:

* Engine stopped;
* exclusive maintenance mode;
* explicit hardware-control lock.

Two independent processes shall not concurrently control the same physical actuator.

A request to stop the Engine is a lifecycle-control request (see "Lifecycle-Control Requests"), not an operational command.

=== Local Safety Exceptions

A narrow local safety mechanism may override normal central decision-making when:

* the consequence of failure is severe;
* the required reaction window is short;
* waiting for the ordinary Engine decision path would be unsafe.

Such behaviour must be:

* deliberately designed;
* narrowly scoped;
* documented;
* testable;
* observable where technically possible.

=== Time-Scale-Tolerant Design

Aquaponics is normally a comparatively slow physical process.

Important system evolution generally occurs over:

* seconds;
* minutes;
* hours;
* days;
* weeks.

The software shall exploit these physical time scales.

Correctness should not unnecessarily depend on:

* millisecond timing;
* tightly coupled concurrent tasks;
* aggressive polling;
* fragile scheduling assumptions;
* race-prone coordination.

This does not require slow software.

It requires software whose correctness does not depend on unnecessarily precise execution timing.

=== Time Handling

Time handling shall be explicit.

The system shall distinguish:

* absolute real-world time;
* elapsed duration;
* scheduling time;
* persisted timestamps.

Durations should use monotonic time where appropriate.

Examples include:

* pump runtime;
* retry delay;
* control-loop duration;
* timeout;
* heartbeat age.

Absolute events should use explicit timezone-aware timestamps.

Internal persisted timestamps should preferably use a normalized representation such as UTC.

Local time belongs primarily to:

* human-facing display;
* local schedule interpretation;
* reporting.

Wall-clock access should not be scattered unpredictably throughout domain logic.

=== Hardware Abstraction

Core domain logic shall not directly contain platform-specific operations such as:

[source,text]
----
GPIO.output(...)
----

Instead, it should express domain operations such as:

[source,text]
----
pump.turn_on()
----

Hardware-specific implementations shall exist behind defined interfaces.

Examples include:

* temperature sensor;
* relay;
* pump;
* aerator;
* light;
* water-level sensor;
* pH sensor;
* camera source.

The Raspberry Pi 40-pin connector itself is not an architectural interface.

=== Environment Boundary

The Engine shall interact with the physical world through defined boundaries.

The production composition shall connect those boundaries to real hardware.

The core Engine shall not be intentionally contaminated with production branches such as:

[source,text]
----
if simulation:
    ...
else:
    ...
----

The production runtime uses real hardware implementations.

Alternative implementations may exist in development or in separate future projects.

=== Production Composition

Only the explicitly designated production composition shall be capable of creating physical hardware adapters.

Conceptually:

[source,text]
----
Production composition
    |
    +-- DS18B20 adapter
    +-- GPIO relay adapter
    +-- production clock
    +-- local persistence
    +-- production configuration
----

Development and test environments shall not accidentally acquire physical GPIO control merely by changing a Boolean configuration value.

=== State Model

The Engine shall maintain explicit logical state.

The state model may include:

* latest valid sensor observations;
* desired actuator state;
* known actuator command state;
* operating mode;
* schedules;
* alarms;
* overrides;
* hardware health;
* configuration references;
* control-policy state;
* incomplete operations.

The system shall distinguish between:

* desired state;
* persisted state;
* observed state;
* historical state;
* physical reality.

A persisted value does not prove current physical reality following a restart or power failure.

=== State History

Relevant history shall be persisted so that an authorized operator can determine:

* what was observed;
* what the Engine believed;
* what decision was made;
* what action was requested;
* whether a fault occurred;
* whether an override was active.

Where practical, important decisions should be explainable from recorded state and policy inputs.

=== Sensor Semantics

Sensor failure shall be represented explicitly.

The following must not be treated as equivalent:

[source,text]
----
temperature = 0
----

and:

[source,text]
----
temperature = unavailable
----

Sensor adapters should detect where technically possible:

* missing device;
* timeout;
* protocol error;
* invalid checksum;
* impossible value;
* implausible jump;
* stale observation;
* invalid format.

Control policies shall define behaviour when required measurements are unavailable.

=== Actuator Semantics

Actuator control shall represent domain intent rather than raw GPIO state.

Where physical confirmation is unavailable, the software shall distinguish between:

* command requested;
* command sent;
* command assumed;
* physically confirmed.

Critical multi-step operations should use recoverable state transitions where appropriate.

Possible states include:

[source,text]
----
REQUESTED
COMMAND_SENT
CONFIRMED
COMPLETED
FAILED
----

The actuator-operation lifecycle is distinct from the higher-level command lifecycle.

For example:

[source,text]
----
Command:
    QUEUED
      |
      v
    EXECUTING
      |
      +---------------------------+
                                  |
                                  v
Actuator operation:          REQUESTED
                                  |
                                  v
                             COMMAND_SENT
                                  |
                                  v
                              CONFIRMED
                                  |
                                  v
                              COMPLETED
                                  |
                                  v
Command:                       DONE
----

Not every actuator supports physical confirmation.

Therefore the exact actuator lifecycle depends on device capabilities, while the Engine command lifecycle remains an Engine-level concern.

=== Logging

Logging shall describe software and operational events.

Each subsystem is responsible for emitting meaningful events.

Examples include:

* subsystem started;
* device detected;
* device unavailable;
* measurement rejected;
* actuator command issued;
* control decision made;
* override activated;
* recovery attempted;
* watchdog event;
* shutdown requested.

Logs shall be aggregated centrally.
This means one process-wide logging configuration, with the operating system's journal (journald) as the system collector.
It does not mean remote log aggregation; the Engine does not depend on any external logging service.

Logs must be bounded and rotated.

No subsystem may consume unlimited storage through logging.

Every diagnostic record shall identify the Engine execution that produced it, using the same execution identifier as the lifecycle audit history, and, where applicable, the operating cycle (see "Operating-Cycle Phases").

A condition that persists can produce the same warning many times.
Only explicitly chosen, known, repetitive and low-information warnings may be subject to repeat suppression, each under its own predefined category, with suppressed occurrences counted and summarized.
Meaningfully different failures shall not be combined under one category.
Errors, lifecycle transitions, Engine failures, security-relevant events and lifecycle audit failures shall not be suppressed.

Diagnostic logs are not authoritative and are not used to decide what the Engine does.

[IMPORTANT]
====
Writing diagnostic logs shall not block physical control for an unbounded time. +
The initial implementation logs synchronously, so a stalled log destination can block the Engine.
This must be resolved before physical equipment control is enabled.
====

=== Telemetry

Telemetry and logging are different concerns.

Examples of telemetry include:

* temperature;
* pH;
* redox;
* water level;
* flow;
* CPU temperature;
* memory usage.

High-frequency observations need not always be persisted at their original frequency.

Telemetry may be:

* retained in memory;
* aggregated;
* downsampled;
* selectively persisted.

=== Logging, History, and Traceability

Three kinds of record serve different purposes and shall be distinguished.

Operational diagnostic logging::
Software execution details, warnings, exceptions, resource problems, startup and shutdown events, and operational health (see "Logging").

Durable command and execution history::
Accepted commands, execution attempts, results, and relevant physical feedback.
It shall support analysis of interrupted or ambiguous operations.
Repeating an interrupted command shall not be assumed to be safe (see "Command Lifecycle" and "Command Idempotency").

State and observation history::
Measurements, relevant state transitions, and snapshots that support investigation and recovery (see "State History").

Diagnostic logs may mention events such as command issue, but they are not the durable command history.

The architecture shall support correlating related records across Engine executions and restarts.

Logging and persistence shall remain operationally bounded over long periods (see "Disk Protection").

Database schemas and logging libraries are not prescribed here.

The lifecycle audit history is a further, separate record (see "Engine Lifecycle Audit History").
It is not a diagnostic log and not a command history.

=== Engine Lifecycle Audit History

Every Engine execution shall produce a persistent lifecycle audit history.

The history consists of append-only records of lifecycle events.
At minimum it records:

* the Engine starting;
* the Engine entering continuous operation;
* receipt of an operator stop request;
* initiation of shutdown;
* completion of shutdown;
* an Engine failure, when it is detectable.

Each record shall identify:

* an absolute UTC timestamp;
* a unique Engine execution identifier;
* the event type;
* the shutdown or failure reason, where available;
* the requesting Linux identity, where applicable;
* relevant event context.

For an operator stop request, the Engine's authoritative receipt time shall be distinguishable from any submission time reported by the client.

The lifecycle audit history:

* survives ordinary Engine process restarts;
* is historical evidence and shall never be interpreted as pending commands;
* is never replayed;
* is distinct from diagnostic logging and from the durable command journal.

Critical lifecycle records shall be written with explicit attention to flushing and storage durability.
The guarantees actually provided shall be documented.

An inability to persist a lifecycle record shall be reported clearly.
It shall not indefinitely prevent a necessary shutdown or cleanup.

After abrupt termination, such as `SIGKILL` or power loss, final lifecycle events may be absent.
Retrospectively identifying an unclean previous execution is a recovery concern (see "Restart and Startup Reconciliation") and is not part of this history's minimum requirements.

The storage format is not prescribed here.
The initial implementation is described in "Lifecycle Audit Persistence" in the Development and Operations chapter.

=== Persistence

The production Engine shall use local authoritative persistence.

An embedded database such as SQLite is an appropriate initial implementation.

Core operation shall not require a remote database server.

The production database may contain:

* configuration;
* measurements;
* control history;
* logical runtime state;
* calibration;
* alarms;
* schedules;
* durable commands;
* command execution history.

The operational database is private Engine infrastructure.

External software shall not manipulate control state, submit commands, or trigger physical actions by directly editing database rows.

External state-changing requests shall enter through the Engine ingress boundary.

Conceptually:

[source,text]
----
External Client
      |
      v
API / CLI / SHMC
      |
      | submit intent
      v
Engine Ingress
      |
      | validate and accept
      v
Engine-owned Durable Command Journal
      |
      v
Engine Command Executor
      |
      v
Physical Action
----

The Engine may use its own local database internally as a durable command journal.

This internal use of persistence is part of the Engine implementation and does not make the database a public command interface.

The distinction is:

[source,text]
----
FORBIDDEN

External Component
        |
        v
Operational Database
        |
        v
Physical Action
----

versus:

[source,text]
----
INTENDED

External Component
        |
        v
Engine Ingress
        |
        v
Engine-owned Persistence
        |
        v
Command Execution
        |
        v
Physical Action
----

The Engine shall remain the sole authoritative owner of:

* command acceptance;
* command persistence;
* command ordering;
* command execution;
* command recovery;
* operational state mutation.

External systems may receive data through supported query interfaces, exports, replicas, backups, or telemetry channels, but shall not use direct database access as the normal integration mechanism.

=== Local Database Requirement

The physical controller shall continue operating if the LAN disappears.

Therefore the authoritative operational state required for control shall reside locally on the controller.

External systems may receive:

* replicas;
* exports;
* backups;
* telemetry copies.

Those copies are not required for core operation.

=== Database Integrity

Persistent updates shall be transactional where appropriate.

The Engine shall detect:

* database-open failure;
* incompatible schema;
* invalid critical records;
* interrupted migration;
* corruption where detectable.

The system must define when to:

* reconstruct noncritical state;
* enter degraded operation;
* restore from backup;
* refuse unsafe automatic operation.

=== Persistence for Recovery and Investigation

The Engine shall persist sufficient information to support the defined recovery process and operational investigation.

The persistence responsibilities are distinct:

[cols="2,3",options="header"]
|===
|Information |Role in recovery and investigation

|System configuration
|Defines how the Engine is to operate.

|Last-known operational state
|Starting point for reconciliation. It is not current physical truth (see "Restart and Startup Reconciliation").

|Accepted commands
|Accepted work that shall not be silently lost (see "Durable Command Journal").

|Command execution attempts and outcomes
|Show what was attempted and what resulted, including ambiguous outcomes (see "Command Lifecycle").

|Measurements and their validity
|Allow observations to be judged for validity and freshness.

|Significant state transitions
|Explain how the system reached its current state.

|Faults and recovery activities
|Record unresolved faults, retries, escalation, and recovery.

|Historical observations and snapshots
|Support investigation of past behaviour.
|===

Not every temporary runtime variable needs to be persisted.

Persisted information shall be sufficient to support the defined recovery process, subject to storage integrity and hardware availability.

Recovery guarantees shall be realistic.
For example, destroyed storage or inaccessible critical hardware may prevent complete recovery.
The Engine shall detect such limitations (see "Database Integrity") and shall not silently assume normal operating conditions.

This section does not redefine the unified command path or the durable command journal.

=== Backup

A live database is not a backup.

A copy stored on the same failed storage device is not sufficient disaster protection.

The backup hierarchy should eventually include:

[source,text]
----
Live Database
     |
     +--> rotating local snapshots
     |
     +--> independent off-device backup
----

SQLite backups shall use transactionally safe mechanisms.

Backups should be:

* timestamped;
* rotated;
* validated;
* periodically restored in a test environment.

=== Runtime Reliability Layers

The controller shall be designed around the assumption that individual components eventually fail.

The protection hierarchy is:

[source,text]
----
Physical safety
      |
      v
Hardware-defined safe behaviour
      |
      v
Operating-system recovery
      |
      v
Engine/process recovery
      |
      v
Application-state recovery
      |
      v
Monitoring and notification
----

=== Engine Lifecycle

The Engine lifecycle consists of startup, a continuous operating loop, and termination.

Planned and unexpected termination have different consequences:

[source,text]
----
Startup (including state reconciliation)
   |
   v
Continuous operating loop
   |
   +--> Planned, controlled shutdown
   |         |
   |         v
   |      Engine stopped
   |      (remains stopped until deliberately started)
   |
   +--> Unexpected termination
             |
             v
          Restart according to the configured
          supervision and recovery policy
             |
             v
          Startup (including state reconciliation)
----

The intended operation is continuous and indefinite.

Intentional maintenance shutdowns are nevertheless valid.

Unexpected termination is an interruption from which the Engine is designed to recover.
It is not the expected end of normal operation.

Every startup, whether after an unexpected termination or after a deliberate start, performs the required state reconciliation (see "Restart and Startup Reconciliation").

==== Planned Termination

The Engine shall support deliberate, controlled shutdown (see "Clean Shutdown").

A deliberate, controlled shutdown leaves the Engine stopped.
A deliberate stop shall not automatically trigger a restart.
Process supervision shall therefore not treat a deliberate stop as a failure to be recovered.

The Engine remains stopped until it is deliberately started again, for example by an operator or by the next boot-time service startup.

An operator request for a controlled shutdown is a lifecycle-control request (see "Lifecycle-Control Requests").
It is never replayed after a restart.

During a controlled shutdown, the Engine shall complete or safely interrupt ongoing activities according to their individual requirements, preserve necessary information, and release resources appropriately.

Physical equipment shall be left in its defined safe condition, as established by its equipment-specific failure policy (see "Equipment-Specific Failure Policy").

==== Unexpected Termination

The Engine may stop without warning because of, for example:

* power failure;
* operating-system failure;
* memory exhaustion;
* hardware failure;
* software defects;
* external process termination;
* other unexpected interruptions.

Application-level shutdown handlers cannot be assumed to execute after such failures.

The architecture shall therefore support recovery without depending on successful shutdown processing.

Every startup is consequently treated as a possible recovery from an interrupted execution (see "Restart and Startup Reconciliation").

==== Restart After Unexpected Termination

Unexpected termination may trigger an automatic restart, according to the configured supervision and recovery policy.
That policy remains bounded (see "Process Supervision" and "Recovery Escalation").

Following such a restart, the Engine shall attempt to restore autonomous operation, subject to the safety conditions described in "Restart and Startup Reconciliation" and "Fault Isolation and Functional Availability".

Operating-system supervision (see "Process Supervision") and the hardware watchdog (see "Hardware Watchdog") may contribute to restarting the process.

They do not replace application-level recovery.

=== Process Supervision

The production Engine shall run as a proper Linux service.

`systemd` is the preferred production supervisor.

The service shall support:

* boot-time startup;
* restart following process failure;
* controlled termination;
* journal integration;
* bounded restart policy.

Manual shell execution shall not be the normal production operating method.

=== Meaningful Health Heartbeat

The existence of a Python process is not sufficient proof of health.

The Engine shall eventually provide a meaningful health heartbeat.

A heartbeat should demonstrate that useful control activity continues to execute.

Conceptually:

[source,text]
----
Control cycle succeeds
        |
        v
Heartbeat refreshed
        |
        v
Supervisor checks heartbeat age
        |
        v
Heartbeat expires
        |
        v
Engine considered unhealthy
----

=== Hardware Watchdog

A process supervisor cannot recover a frozen operating system.

A Linux/Raspberry hardware watchdog should therefore be available as a later protection layer.

Conceptually:

[source,text]
----
Aquaponics Engine
       |
       v
systemd supervision
       |
       v
Linux watchdog
       |
       v
hardware watchdog
       |
       v
automatic reboot
----

Watchdog configuration shall be tested deliberately.

A watchdog must not be used to hide an unexplained recurring failure.

=== Restart and Startup Reconciliation

Startup is safety-critical.

The Engine shall not assume that the previous execution ended cleanly.

The startup sequence should conceptually be:

[source,text]
----
Linux boots
    |
    v
hardware interfaces initialize
    |
    v
Engine starts
    |
    v
configuration validated
    |
    v
persistent state validated
    |
    v
devices rediscovered
    |
    v
sensor sanity checks
    |
    v
outputs established in known state
    |
    v
incomplete operations reconciled
    |
    v
normal control begins
----

Every startup, whether ordinary or following an unexpected interruption, shall attempt to establish the actual state of the physical installation.

Building on the distinctions made in "State Model", startup reconciliation shall distinguish:

* persisted or last-known state;
* intended or desired state;
* currently observed physical state;
* unknown or unverified state.

Persisted information shall not automatically be treated as current physical truth.

Measurements shall carry sufficient information to determine their validity and freshness.

The Engine shall attempt to reconcile persisted information with current observations before authorizing operations that depend on it.

Uncertainty shall remain explicitly represented.
It shall not be silently replaced with assumptions.

Recovery may result in:

* restoration of normal operation;
* degraded operation (see "Degraded Operation");
* a condition requiring operator intervention.

The architecture does not prescribe one universal response to every failed peripheral.
The response follows the failure policy of the affected function.

Where the sequence above refers to outputs being established in a known state, that state is determined by the equipment-specific failure policy (see "Equipment-Specific Failure Policy").
It is not a universal ON or OFF default.

=== Clean Shutdown

On normal termination the Engine should have an opportunity to:

* stop initiating new work;
* place actuators into defined states where required;
* finish or safely abort transactions;
* flush critical state;
* close database connections;
* close hardware handles;
* record a clean shutdown.

Shutdown handling shall be bounded.

A hung cleanup operation shall not prevent the machine from shutting down indefinitely.

The defined state of each actuator is determined by its equipment-specific failure policy (see "Equipment-Specific Failure Policy").

=== Recovery Escalation

Automatic recovery must not create uncontrolled reboot loops.

A possible escalation hierarchy is:

[source,text]
----
Process failure
    -> restart Engine

Repeated process failure
    -> degraded or safe mode

Operating system unresponsive
    -> watchdog reboot

Repeated boot failure
    -> avoid blind unsafe restart loop
----

Restart count and reset cause should be observable where possible.

=== Power Reliability

Power integrity is part of the controller architecture.

The installation shall consider:

* outage;
* short interruption;
* brownout;
* undervoltage;
* poor power supplies;
* voltage drop;
* switching noise;
* rapid cycling.

A UPS or suitable backup-power arrangement should eventually support:

* continuation through short interruptions;
* controlled shutdown during prolonged interruption.

When power returns, unattended boot and Engine recovery shall be possible.

=== Storage

The production controller should avoid ordinary SD-card storage as a critical single point of failure where practical.

The preferred target is:

* boot from SSD or similarly durable storage;
* OS on SSD;
* Engine on SSD;
* local DB on SSD;
* persistent logs/state on SSD;
* no SD card required during ordinary production operation.

Actual support depends on the selected Raspberry Pi hardware.

The SSD may use an independent power source if required by the system power budget.

=== Resource Protection

Long-running resource use shall be observable.

Monitor trends in:

* memory;
* swap;
* file descriptors;
* threads;
* processes;
* sockets;
* DB connections;
* temporary files;
* filesystem space;
* filesystem inodes;
* log growth.

A slow leak that takes weeks to cause failure is still a production bug.

=== Disk Protection

No component may grow storage usage without bounds.

Production shall monitor both:

[source,bash]
----
df -h
----

and:

[source,bash]
----
df -ih
----

where appropriate.

Retention limits shall exist for:

* logs;
* telemetry;
* backups;
* temporary data;
* crash artifacts.

=== Degraded Operation

The Engine shall support explicit degraded states.

Not every fault shall mean either:

* full normal operation;
* complete shutdown.

Examples:

[source,text]
----
Remote UI unavailable
    -> continue physical control

Noncritical sensor unavailable
    -> continue with warning

Historical export unavailable
    -> continue local control

Critical sensor unavailable
    -> conservative/safe policy

Control loop unavailable
    -> defined recovery/failsafe
----

=== Fault Isolation and Functional Availability

A peripheral failure shall not unnecessarily interrupt independent Engine functionality.

The following concepts are distinct:

* the Engine lifecycle state (see "Engine Lifecycle");
* the health of individual components, such as sensors and actuators;
* the operational availability of individual functions.

The Engine may remain operational while some peripherals or functions are unavailable.

A function may operate only while its necessary operational and safety conditions are satisfied.

If a required dependency is unavailable, the affected function shall follow its defined failure policy.
Other functions may continue operating when they can do so safely.

The architecture does not define a global "everything ON" or "everything OFF" recovery policy.
Terms such as "conservative/safe policy" and "failsafe" in "Degraded Operation" refer to the policy of the affected function.

=== Equipment-Specific Failure Policy

[IMPORTANT]
====
Fail-safe does not universally mean switching equipment OFF. +
Inactivity, or declining to issue a further command, is not automatically safer than continued operation.
====

The appropriate behaviour depends on:

* equipment characteristics;
* current physical conditions;
* consequences of action;
* consequences of inaction;
* available independent protections;
* potential harm to animals, plants, people, and equipment.

The following example illustrates the principle.
It is not a heater-control policy and does not imply any particular equipment.

During freezing conditions, continued heating may be safer than disabling heating.
However, uncontrolled heating without valid temperature feedback may also be dangerous.
An independent thermostat or thermal cutoff may allow heating to continue safely even when the software temperature sensor becomes unavailable.

Each meaningful physical function shall eventually have a documented, equipment-specific failure policy.

Such a policy may prescribe:

* an active response;
* passive behaviour;
* continued operation under independent safeguards;
* suspension of the affected function.

The appropriate behaviour shall be established through physical safety analysis.
It shall not be guessed during implementation.

=== Physical and Software Fail-Safe Cooperation

The Engine and the physical installation shall be designed together.

Physical safety mechanisms shall account for the possibility that software cannot respond at all.

Examples include:

* relay de-energized states;
* normally open or normally closed contacts;
* independent thermostats;
* protective switches and interlocks;
* appropriate power-loss behaviour;
* other independent safety mechanisms.

Physical inaction may itself implement a deliberate safe default, provided the physical design establishes that behaviour.

The Engine shall not assume a particular passive equipment state unless it is supported by the documented physical configuration.

Device-specific safety requirements and wiring belong in the Physical Infrastructure chapter (see "Relay System", "Physical Fail-Safe Behaviour", and "Boot-State Behaviour" there).

Software mechanisms that override the normal decision path remain subject to "Local Safety Exceptions".

=== Fault Monitoring, Retry, and Escalation

Fault handling shall include more than a single error-log entry.

The architecture shall support:

* detection of peripheral failures;
* explicit representation of unresolved faults;
* appropriate retry strategies;
* continued monitoring while a fault persists;
* escalation of persistent or critical conditions;
* recognition and recording of recovery.

Retries shall be bounded or otherwise controlled.
Retry delays and timeouts are durations and follow "Time Handling".

A failing peripheral shall not trap the Engine in a blocking retry loop.

Failure supervision shall not prevent independent life-support functions from operating.

Escalation of process-level failure is described in "Recovery Escalation".
This section concerns faults of peripherals and functions.

=== Operator Notification

Significant operational faults shall be reported promptly to the operator.

The architecture shall support:

* notification of important faults;
* escalation when necessary;
* notification of significant recovery events;
* durable recording of notification-related events;
* retries when delivery temporarily fails.

Remote notification cannot be assumed to succeed, for example during an Internet outage.

The Engine shall remain autonomous without external communication services.

Where necessary, physical or local alerting mechanisms may provide additional protection.

Notification delivery shall never be a prerequisite for executing essential local safety functions.
Notification handling shall not block the control loop (compare "Bounded External Ingress").

Notification providers and protocols are not selected by this document.

=== Incremental Implementation of Resilience Requirements

The requirements in the sections "Engine Lifecycle" through "Operator Notification" describe the intended behaviour of the completed Engine.

They do not require every subsystem to be implemented at once.

The project is developed incrementally through small, reviewable tasks.

The initial Engine implementation may be limited to:

* a class representing the Engine;
* a startup method;
* a continuous execution loop;
* controlled exit handling.

Persistence, command execution, recovery, peripheral management, monitoring, and notification may be introduced by later tasks.

Early implementations shall not contradict the documented long-term architecture.

Functionality that has not been implemented shall not be simulated or described as implemented.

The following physical design decisions remain open and are to be resolved in the Physical Infrastructure chapter:

* the equipment-specific failure policy of each controlled function;
* the relay contact configuration, de-energized state, and required safe state of each channel;
* the independent physical safeguards available for each function;
* any physical or local alerting mechanisms.

=== API Boundary

The API is the canonical supported external interaction boundary.

It shall expose authorized operations for:

* current state;
* history;
* health;
* devices;
* alarms;
* supported configuration;
* interventions;
* overrides;
* diagnostics.

The API shall not become the control loop.

The Engine continues operating when no requests arrive.

=== Web Frontend

The web frontend shall consume the same supported API used by other clients.

It shall not:

* directly access the database;
* import internal backend implementation details;
* manipulate GPIO;
* use a private bypass interface.

The frontend shall be capable of operating locally without Internet access.

Where hosted on the same machine as the backend, it shall be able to connect through the local interface, for example:

[source,text]
----
127.0.0.1
----

The same web application may also be exposed over the local wired LAN subject to authorization.

=== Mobile Application

The mobile application is an external API client.

It shall not be required for physical operation.

It may provide functionality equivalent or similar to the web frontend.

The mobile application shall use supported API semantics rather than application-specific shortcuts into the Engine.

=== Administrative CLI

A local administrative CLI shall exist for maintenance and diagnostics.

It may expose privileged operations unsuitable for ordinary remote clients.

Possible functions include:

* health inspection;
* raw sensor diagnostics;
* hardware diagnostics;
* DB validation;
* maintenance mode;
* controlled actuator test;
* configuration inspection.

The CLI should reuse domain/service logic rather than create a second controller implementation.

Authorization of local administrative access is described in "Local Administrative Access".

=== Authentication and Authorization

External interaction shall be authenticated and authorized.

Capabilities should distinguish at least conceptually:

* read-only monitoring;
* operational intervention;
* configuration;
* maintenance;
* administration.

Local physical control shall not depend on continuously contacting a remote authentication server.

==== Independent Authorization Boundaries

Three security responsibilities are distinct and independent:

. Linux access control, which authorizes local processes and service identities;
. REST API application authorization, which authorizes individual application users;
. Engine command enforcement, which determines which command capabilities are available to the connecting service or interface, and validates commands against operational and safety requirements.

Conceptually:

[source,text]
----
Local operator                      Application user
      |                                    |
      | Linux identity                     | application authentication
      | and permissions                    | and authorization
      |                                    | (REST API, boundary 2)
      |                                    v
      |                              REST API service
      |                                    |
      |                                    | Linux service identity
      |                                    | and permissions
      v                                    v
          Restricted local IPC (boundary 1)
                       |
                       v
                    ENGINE
       enforces command capabilities and
         validates commands (boundary 3)
----

The Engine does not maintain a separate user-authentication system.
It may rely on Linux-authenticated client identities, restricted interfaces, and the capabilities assigned to them.
No additional Engine username and password system is implied.

Satisfying one boundary does not satisfy the others.

The administrative CLI and the REST API remain separate Engine clients with separately assigned capabilities.

An API user's administrative role shall not automatically confer Linux administrative privileges.
An application administrator does not thereby become a Linux administrator.

The maximum capabilities available through the REST API are constrained by the permissions granted to the API service.

A valid API request shall satisfy all applicable authorization and Engine safety requirements.

==== Local Administrative Access

The Engine shall support a local administrative CLI (see "Administrative CLI").
The CLI is a client of the Engine, not a separate controller.

Local administrative authorization shall rely on Linux identities, privileges, and access controls.
Authorized operators shall not require a separate Aquaponics application login for local administrative operations.

Linux authorization may use dedicated groups or service permissions.
Engine administration does not necessarily require general root access.

Local commands shall reach the Engine through a restricted IPC interface, accessible only to authorized local identities.
The exact transport remains an implementation decision (see "Transport Is Not Command Semantics").

Linux access control permits a client to use the administrative interface.
It does not exempt an operation from Engine command enforcement and validation, the unified command path, or the maintenance conditions described in "CLI Command Semantics".

Illustrative implementation examples, which are not architectural decisions, include filesystem permissions on a local socket, membership of a dedicated Linux group, and the credentials of the connecting process.

==== REST API Service Identity and Authorization

The Engine and the REST API shall run under separate Linux service identities.

The REST API service identity shall be restricted to the capabilities required by its intended operations.

Application users authenticated through the REST API are not automatically represented by corresponding Linux user accounts.

The REST API shall enforce application-level authentication and authorization (see "API Command Semantics").
Its endpoints shall expose only explicitly supported functionality.

The API service's own Linux permissions and the command capabilities the Engine assigns to it shall independently restrict which commands it may submit.
API-level authorization is therefore not the only restriction on what the REST API can cause the Engine to do.

The Engine retains independent command enforcement for the API service as a connecting interface (boundary 3 in "Independent Authorization Boundaries").
It does not authenticate individual application users.

==== Elevated REST Operations

Administrative REST operations may be introduced deliberately in future development.

Such operations require explicit authorization and appropriately restricted Engine-side capabilities.

They shall not implicitly grant arbitrary Linux administration or unrestricted access to the Engine's administrative interface.

The exact future REST API role hierarchy and permission matrix remain undecided.

==== Shared Client Protocol

The CLI and the REST API may use a common client protocol or command representation.

The REST API is conceptually a restricted Engine client.
It need not execute terminal commands as subprocesses.

Both interfaces remain subject to the Engine's authoritative command-handling requirements (see "Unified Command Execution Architecture" and "Durable Command Journal").
Sharing a protocol creates no exception to command persistence or physical safety rules.

==== Authorization Details Not Prescribed

This document does not prescribe:

* local socket paths;
* Linux user or group names;
* IPC libraries;
* API endpoint names;
* authentication frameworks;
* role definitions;
* command schemas.

These remain implementation or later design decisions.

=== Open Architecture
