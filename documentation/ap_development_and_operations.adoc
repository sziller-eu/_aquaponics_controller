== Development and Operations

=== Purpose

This document defines how the Aquaponics software is:

* planned;
* implemented;
* tested;
* reviewed;
* released;
* deployed;
* operated;
* diagnosed;
* recovered.

The development process shall support both human developers and AI coding agents.

Development and operational procedures shall preserve the architectural invariants defined by the project.

In particular:

* the Aquaponics Engine is the authoritative controller;
* the Engine operates autonomously and continuously;
* external interfaces do not drive the control loop;
* state-changing operations use the unified Engine command path;
* the Engine owns its operational persistence;
* the API and Engine are separate production processes;
* production operation does not depend on Internet access;
* development convenience shall not weaken physical-system safety.


=== Development Environment

Primary software development shall occur on a Linux development workstation.

The preferred development environment is Ubuntu or another suitable Debian-family Linux distribution.

The production Raspberry Pi shall not be the normal development workstation.

The production controller shall receive tested, versioned releases.

Development shall not require permanent access to:

* the production Raspberry Pi;
* the physical aquaponics installation;
* the Internet;
* external cloud services.


=== Repository Model

The Aquaponics project should initially use two primary software repositories:

* controller repository;
* mobile application repository.

The controller repository is the authoritative repository for the locally deployed Aquaponics control system.

The mobile application is a separate external client.


==== Controller Repository

The controller repository is a public repository owned by the `sziller.eu` GitHub organization.

Its current repository name is:

[source,text]
----
_aquaponics_controller
----

The repository contains the locally deployable controller system.

A conceptual structure is:

[source,text]
----
_aquaponics_controller/
    src/
        aquaponics_controller/
            engine/
            hardware/
            persistence/
            runtime/
            api/
            cli/
            composition.py

    web/
    deployment/
    tests/
    documentation/
    pyproject.toml
----

Exact directory names may evolve.

Directories shall be created when required by implemented functionality.

The repository shall not be populated with empty abstraction layers merely to mirror this conceptual structure.

The important boundaries are:

* Engine;
* hardware adapters;
* persistence;
* runtime/platform integration;
* API;
* administrative CLI;
* web frontend;
* production composition;
* deployment support;
* tests;
* documentation.


==== Python Source Layout

Python application code should use a `src/` layout.

Conceptually:

[source,text]
----
src/
    aquaponics_controller/
----

This separates importable production code from:

* repository tooling;
* tests;
* documentation;
* deployment files;
* generated artifacts.

The Python package structure shall follow architectural responsibilities rather than arbitrary technical grouping.


==== Mobile Repository

The mobile application shall use a separate repository.

It has a separate:

* build system;
* release lifecycle;
* mobile-platform toolchain;
* signing process;
* distribution process.

The mobile application is an API client of the Aquaponics controller.

The mobile application shall not contain controller-domain logic required for physical operation.


=== GitHub Project

Development shall be managed using a GitHub Project with a Kanban-style workflow.

The Project should coordinate work across:

* the controller repository;
* the mobile repository;
* future closely related Aquaponics repositories where appropriate.

The controller repository is owned by the `sziller.eu` GitHub organization.

Future Aquaponics repositories should normally use the same organizational ownership unless a documented reason requires otherwise.

GitHub is a development, collaboration, source-management, and release-distribution platform.

The production Aquaponics controller shall not depend on GitHub availability during ordinary operation.

=== Development Tasks and GitHub Issues

Development work shall be organized into identifiable, reasonably bounded tasks.

GitHub issues are recommended for substantial, independently trackable work, particularly when the work involves:

* significant implementation changes;
* architectural decisions;
* multiple development stages;
* collaboration between contributors;
* changes requiring formal review or tracking.

GitHub issues are not mandatory.

Development may proceed without a dedicated issue when this is appropriate for the work being performed.

Examples include:

* repository setup;
* exploratory development;
* small maintenance tasks;
* documentation improvements;
* development infrastructure changes;
* other coherent and appropriately scoped tasks.

The absence of a GitHub issue does not relax requirements concerning architectural consistency, implementation quality, testing, documentation, or review.

These rules apply equally to human and AI-assisted development.

Both feature-branch naming conventions are valid:

* `feature/<short-description>`
* `feature/<issue-number>-<short-description>`

Where an issue exists, it should identify:

* problem or objective;
* affected subsystem;
* architectural constraints;
* expected behaviour;
* acceptance criteria;
* testing requirements;
* documentation impact.

Large features should be decomposed into parent and child issues when useful.

Implementation work shall not silently expand beyond the scope of its task or issue merely because adjacent refactoring appears attractive.

=== Branching

The repository uses a three-level branching model:

[source,text]
----
feature/<short-description>
feature/<issue-number>-<short-description>
        |
        |  pull request
        v
    staging
        |
        |  pull request
        v
  production
----

`production`::
The highest-level branch.
It contains approved, stable, production-ready code and is the repository's GitHub default branch.
Direct development on `production` is prohibited.

`staging`::
The integration branch for completed development work.
Completed features are integrated and tested here before promotion to `production`.
Direct development on `staging` should normally be avoided.

`feature/<short-description>` or `feature/<issue-number>-<short-description>`::
Short-lived development branches for individual development tasks or coherent groups of changes.
Every feature branch originates from `staging`.

No additional permanent branches shall be introduced without a documented architectural decision.

Both naming conventions are valid.
An issue number is required in the branch name only when the branch is associated with a dedicated GitHub issue.
A GitHub issue is not required for every development task.
Bug fixes and maintenance work follow the same naming patterns.

Examples:

[source,text]
----
feature/tree
feature/local-health-endpoint
feature/42-water-temperature-adapter
feature/57-startup-db-recovery
----

Completed feature branches are integrated into `staging` through pull requests.

Validated changes are promoted from `staging` into `production` through pull requests.

The `production` branch shall represent a releasable state.


=== Pull Requests

Changes shall enter the shared branches through pull requests only:

* a feature branch is merged into `staging`;
* `staging` is promoted into `production`.

A pull request should:

* target the correct branch (`staging` for feature work, `production` for promotion from `staging`);
* reference the relevant issue where one exists;
* describe the implementation;
* identify important architectural decisions;
* document tests performed;
* identify migration or deployment impact;
* identify safety impact where applicable;
* identify documentation changes.

Large unrelated refactors should not be mixed into feature work without justification.


=== Definition of Done

A task affecting production behaviour is not complete merely because the nominal path works.

Depending on scope, completion may require:

* implementation;
* unit tests;
* integration tests;
* failure-path tests;
* architecture tests;
* documentation;
* configuration update;
* deployment update;
* migration handling;
* recovery verification;
* hardware validation.

Safety-related work may require explicit testing of:

* startup;
* shutdown;
* restart;
* partial failure;
* interrupted execution;
* unavailable hardware;
* unavailable network;
* unavailable API;
* unavailable persistence.


=== Package Management

The Python controller shall be structured as a proper Python project.

`pyproject.toml` shall be used for project metadata and packaging unless a future technical requirement justifies another approach.

Production dependencies shall be:

* explicit;
* reproducible;
* declared in project configuration;
* compatible with the target Raspberry architecture;
* installable without proprietary infrastructure.

Dependency versions should be sufficiently constrained to support reproducible releases.

The final production Python version shall be selected together with the production Raspberry Pi operating system.

Until that decision is finalized, Python `>=3.11` is an acceptable provisional development baseline.

Development-workstation Python version shall not automatically define the production Python version.


=== Dependency Direction

Dependencies shall point inward toward the Engine's domain abstractions.

The Engine shall not depend on:

* API implementation;
* web frontend;
* mobile application;
* concrete GPIO implementation;
* SHMC;
* remote services.

Concrete infrastructure implements interfaces required by the Engine.

Conceptually:

[source,text]
----
             external systems
                    |
                    v
                   API
                    |
                    v
               Engine ingress
                    |
                    v
                  ENGINE
                 /      \
                /        \
               v          v
        persistence     hardware
          adapters       adapters
----

The Engine defines the domain expectations.

Infrastructure supplies concrete implementations.


=== Production Composition

Production dependencies shall be assembled deliberately at an explicit composition boundary.

Conceptually:

[source,text]
----
Production composition
    |
    +-- Engine
    +-- production clock
    +-- local persistence
    +-- real sensor adapters
    +-- real actuator adapters
    +-- production configuration
----

Only explicitly designated production composition shall normally create real hardware adapters.

A development configuration flag shall not casually convert test code into a real GPIO controller.


=== Development Hardware Abstraction

Development on the Ubuntu workstation shall not require physical Raspberry hardware for ordinary domain work.

Hardware interfaces shall therefore have test implementations.

Examples:

[source,text]
----
TemperatureSensor
    +-- DS18B20TemperatureSensor
    +-- FakeTemperatureSensor

Relay
    +-- GPIORelay
    +-- FakeRelay
----

Fake implementations exist for:

* development;
* unit tests;
* integration tests;
* deterministic failure testing.

They are not a production simulation subsystem.


=== Fake Sensor Inputs

A fake sensor may return:

* configured values;
* scripted sequences;
* invalid readings;
* missing readings;
* stale readings;
* failure conditions.

Example:

[source,text]
----
read 1 -> 22.0
read 2 -> 22.1
read 3 -> unavailable
read 4 -> 28.5
----

This allows domain behaviour to be tested without physical hardware.


=== Fake Actuators

Fake actuators shall not access real GPIO.

They may record commands such as:

[source,text]
----
12:03:00 pump -> ON
12:08:00 pump -> OFF
----

This allows deterministic assertions about Engine behaviour.


=== Test Isolation

Test hardware implementations should normally exist outside the production package where practical.

Production packaging shall not accidentally include or expose a casual mechanism for replacing physical hardware with test hardware.

Test code shall never acquire physical GPIO access merely because a developer executes an ordinary test suite.


=== Test Categories

The project shall distinguish several test levels.


==== Unit Tests

Unit tests cover isolated:

* domain logic;
* policies;
* validation;
* calculations;
* state transitions;
* command semantics;
* schedule calculations;
* time handling.


==== Integration Tests

Integration tests cover interactions between components.

Examples include:

* Engine and persistence;
* Engine ingress and command journal;
* Engine and API transport boundary;
* command executor and hardware abstraction;
* startup/recovery components;
* migrations;
* configuration loading.


==== Architecture Tests

Architecture tests enforce structural invariants.

Examples include:

* Engine domain code does not import API implementation;
* Engine domain code does not import concrete GPIO adapters;
* API does not directly access GPIO;
* API does not manipulate operational database tables;
* external state-changing paths terminate at Engine ingress;
* production composition is the normal creator of real hardware adapters;
* test fakes do not enter the production runtime accidentally.


==== Hardware Tests

Hardware tests run deliberately on Raspberry hardware for:

* GPIO;
* relay control;
* real sensors;
* camera access;
* storage behaviour;
* watchdog;
* boot behaviour;
* power behaviour where safely testable.

Hardware tests shall be clearly separated from ordinary workstation test execution.


==== Recovery Tests

Recovery tests exercise realistic failure conditions.

Examples include:

* terminate the Engine process;
* freeze a test control loop;
* disconnect a sensor;
* disconnect the network;
* terminate the API;
* interrupt IPC;
* fill a test filesystem;
* corrupt a test database;
* reboot during activity;
* trigger watchdog recovery;
* boot without Internet;
* force repeated Engine startup failure;
* restore from backup.

The relevant question is:

[IMPORTANT]
====
Does the controller return to a safe and useful state after realistic failure?
====


=== Production Composition Testing

Tests shall ensure that production composition uses only approved production implementations.

The production application must not accidentally deploy:

* fake sensors;
* fake relays;
* test clocks;
* test databases;
* experimental control policies.

Production composition shall be explicit and inspectable.


=== Running the Automated Tests

Install the development dependencies and run the suite from the repository root (see the repository `README.md`):

[source,text]
----
$ python -m pip install -e ".[dev]"
$ python -m pytest
----

No test requires real aquaponics peripherals, GPIO, Internet connectivity, root privileges or a second Linux account.
Every test that starts a process bounds its waits and kills the process at teardown.
Sockets and audit files are created in private temporary directories.

The Engine foundation tests cover:

* `test_engine_lifecycle.py`: Engine lifecycle in one process with a scripted stand-in for the IPC ingress: single startup, repeated cycles, STOP handling, signals, unexpected exceptions, failed cleanup, startup conflicts, audit failures, refusal of unauthorized peers and unsupported operations, pacing and CPU use, interruptible idle waiting, non-replay of earlier STOP records. It also covers the request dispatcher (`ping` and `echo` results, argument validation including Unicode and the 256-character boundary, authorization of queries, request classes, no audit or persistence of queries, diagnostic traces) and the responsive idle wait (requests serviced while idling without starting a cycle, the unchanged cycle deadline under request bursts, readiness without progress, a wake-up arriving at any moment, failure while servicing, release of the wake-up resources).
* `test_cycle_phases.py`: the operating-cycle phases in one process: the approved phase order, each phase once per cycle, counting a cycle only after its last phase, request servicing only in `INGEST_EXTERNAL_INTENTS` and never as a phase while idling, an exception in each phase (later phases skipped, cycle not counted, `cycle_phase` and `cycle_number` recorded), overrun warnings for each phase with a simulated clock, no catch-up after a long cycle, STOP and signals during each phase, the time limits and their relation to the ingress bounds and the `ape` timeout, placeholders that do nothing and leave no trace on disk.
* `test_diagnostic_logging.py`: diagnostic logging: the record format and its fields, the execution identifier on every record and identical to the audit history's, the cycle field inside cycles and `-` outside them, failures logged with their cycle number for every phase, no `INFO` output from idle cycles, no logging from signal handlers, opt-in repeat suppression (first occurrences, counting, summaries, flush, levels that may not be suppressed, separate categories per `accept()` errno, unlisted errors and refused requests never suppressed, bounded retention without exception objects), failing destinations (one report without record content or traceback, no exception raised, counts at shutdown, the Engine unaffected), the log file's size bound, rotation failure, permissions, refusal of unsafe destinations (symbolic links and hard links, also after rotation; named pipes with and without a reader; devices; directories; permissions that cannot be restricted), restriction of a permissive existing file, existing directories left unchanged, and fallback to standard error when the file cannot be opened or is refused, and end to end the execution identifier and request trace without the `echo` text; journald priorities (Issue #9): the level-to-priority mapping, every line of a traceback prefixed, prefixes only when standard error really is the journald stream (not merely when `JOURNAL_STREAM` is inherited), the log file unchanged, and an Engine process under a simulated journald stream.
* `test_idle_wait.py`: the readiness-driven idle wait with real sockets: timeout, wake-up before and during a wait, consumption of wake-ups, readiness of the ingress socket, ignoring it on request, release of descriptors.
* `test_local_ingress.py`: the real Unix socket in one process: protocol errors, oversized requests, stalled and disconnecting clients, connection and time bounds (including the idle-wait time limit), `0700`/`0600` permissions, validation of the IPC directory (symbolic links, non-directories, other owners, directories writable by others refused; readable ones restricted; lock-file and stale-socket checks), peer credentials, single-instance refusal, stale endpoint replacement, cleanup, the readiness source, correlation identifiers, and traces that never contain request arguments.
* `test_lifecycle_audit.py`: record content, appending across executions, flushing, failure to persist, partly written lines.
* `test_ipc_protocol.py`: encoding, validation, endpoint resolution, the optional correlation identifier and arguments, and the size limit for the largest valid messages.
* `test_cli.py`: the `ape` client against canned servers: what it sends, how it displays `ping`, `echo` and STOP answers, its exit status for every refusal and unintelligible answer, correlation checking, bounded waits, usage errors.
* `test_engine_processes.py`: the Engine and `ape` as separate operating-system processes: `ape -x`, `SIGINT`, `SIGTERM`, an injected unexpected exception, a conflicting second start, `SIGKILL` followed by a restart, restart without replaying STOP, malformed requests against a live Engine, and every `ape` failure mode with bounded waits.
* `test_failure_handling.py`: lifecycle and IPC failure handling (Issue #8): `ape` retrying only the connection while the Engine's connection queue is full, its single overall deadline, a request never resent, immediate exit 3 or 4 for an unavailable Engine or a permission problem, `internal_error` answers (exit 6); exactly the approved recoverable connection errors contained per connection and every other error propagated; the fixed `internal_error` answer before a request-handler failure, without exception details, and the original exception kept; interruptions never answered; withdrawing the endpoint; the final servicing pass of a controlled shutdown (its limits, authorization, STOP answered "already initiated" and audited, clients beyond the limit unanswered, none after a failure, a failure during it recorded as `ENGINE_FAILURE` with phase `shutdown`); recovery from descriptor exhaustion without spinning; repeated STOP and `SIGINT`/`SIGTERM` with queued and stalled clients end to end; an unsafe IPC directory stopping startup cleanly; and (Issue #9) exactly the approved `accept()` errors contained, every other one propagated, and a broken listener ending the Engine with exit status 1 and cleanup, whether it fails inside a cycle or while idling.
* `test_service_notify.py`: the systemd notification contract (Issue #9) against a fake notification socket: activation from `NOTIFY_SOCKET`, `WATCHDOG_USEC` and `WATCHDOG_PID` (a watchdog for another process disables only the watchdog), malformed variables, the watchdog interval rule, READY and STOPPING once each, heartbeats only between them and at most once per quarter of the actual timeout, abstract socket names, a full or vanished notification socket never blocking or raising for heartbeats and STOPPING; in the Engine: READY after `ENGINE_RUNNING` with the endpoint listening, one heartbeat per completed cycle and none for idle servicing, a failed cycle or the final shutdown pass, STOPPING for every shutdown reason (and no STOPPING attempt, and no warning, when startup failed before the notification socket was opened), a failed READY as a startup failure with cleanup once; and as processes: exit status 2 for an impossible watchdog interval or a malformed `NOTIFY_SOCKET`, exit status 3 for an endpoint conflict without a misleading notification warning, the full READY/heartbeat/STOPPING sequence, and exit status 1 when the service manager cannot be reached.
* `test_systemd_unit.py`: the reviewed unit and `sysusers.d` file, statically: exactly the reviewed directives, device access disabled (`PrivateDevices=yes`), no network access or dependency, an unprivileged dedicated user, SIGTERM-only stopping, the `ExecStart` paths, the cycle interval within the watchdog rule, owner-only directories, the restart exclusions matching the Engine's exit statuses; the Engine not handling `SIGHUP` (a death by signal) and a handled `SIGTERM` exiting 0; and `systemd-analyze verify` without complaints where available (with a check that it would catch a misspelt directive).
* `test_systemd_integration.py` (opt-in, `AQUAPONICS_SYSTEMD_TESTS=1`): the Engine in transient systemd user units built from the reviewed unit; see "Validation" under "Engine Service (Initial Implementation)". Skipped by default.
* `test_request_processing.py`: the Engine and clients as separate processes: `ape --ping` and `ape --echo`, invalid requests, queries that leave no trace on disk or in the audit history, a 30-second cycle interval that does not delay answers or STOP, no extra operating cycles from requests, idle CPU use, descriptor stability, cycles that keep their pace under request streams and stalled clients, and a burst of 40 simultaneous clients that are all answered.

What the tests cannot show:

* A real permission denial for a different Linux user. The tests check permission modes, the peer credential check and a socket with no permissions for its own user. Verify the cross-user case by hand as described in "Local Administrative IPC (Initial Implementation)".
* Behaviour after power loss, or the physical durability of `fsync`.
* Behaviour under `systemd` supervision, unless the opt-in user-level integration tests are run. Even then, the production service identity, system-level sandboxing, start at boot and Raspberry Pi behaviour are covered only by the manual demonstration (see "Engine Service (Initial Implementation)").

The permission-denial test is skipped when run as `root`, because `root` bypasses file permission checks.


=== Unified Command-Path Development Rule

Any normal feature capable of changing physical or logical operating state shall integrate with the unified Engine command path.

A developer shall not introduce a second execution path for convenience.

Examples of incorrect implementations include:

[source,text]
----
API endpoint -> relay adapter directly

CLI command -> GPIO directly

scheduler -> pump directly

policy -> light directly
----

The intended structure is:

[source,text]
----
origin
  |
  v
Engine intent
  |
  v
durable command
  |
  v
Engine executor
  |
  v
hardware adapter
----

Normal state-changing operations shall use this path regardless of whether they originate from:

* API;
* CLI;
* schedule;
* autonomous control policy;
* SHMC;
* AI integration;
* future management interface.


=== Safety-Mechanism Exception

A narrowly scoped low-level safety mechanism may bypass the normal command path only when explicitly permitted by the architecture.

Such an exception shall be:

* safety-motivated;
* narrowly scoped;
* explicitly documented;
* separately tested;
* observable where technically possible.

A developer shall not classify ordinary control functionality as a safety mechanism merely to bypass the command architecture.


=== Durable Command Acceptance

A state-changing operation shall not be treated as accepted merely because:

* HTTP successfully received the request;
* IPC successfully transported the request;
* an in-memory queue received a message;
* a Python function accepted an argument.

A state-changing command is considered accepted only after the Engine has durably recorded it according to command semantics.

Conceptually:

[source,text]
----
external request
      |
      v
API receives request
      |
      v
IPC transports intent
      |
      v
Engine validates intent
      |
      v
Engine persists command
      |
      v
COMMAND ACCEPTED
----

If durable persistence fails, the caller shall not receive a false acceptance result.


=== Engine Database Ownership

The Engine owns the operational persistence layer.

External components shall not:

* insert commands directly into database tables;
* modify operational state directly;
* use database rows as an actuator-control mechanism;
* depend on private schema as a supported interface;
* use direct database access as the normal query interface.

The Engine may internally use the local database for:

* durable command journal;
* runtime state;
* measurements;
* schedules;
* history;
* alarms;
* recovery information.

The database may therefore participate in command execution internally without becoming an external command bus.


=== Query Development Rule

Read-only functionality shall use the Engine query surface.

Examples include requests for:

* current logical state;
* latest known measurement;
* alarms;
* health;
* command status;
* historical observations.

API and CLI implementations shall not become coupled to SQLite schema details merely because direct SQL appears simpler.

Schema evolution must remain possible without requiring external clients to understand internal persistence.


=== Query Versus Active Operation

Contributors shall distinguish a passive query from an operation that causes new physical work.

For example:

[source,text]
----
return latest known water temperature
    -> query
----

while:

[source,text]
----
read physical water-temperature sensor now
    -> active operation
    -> command path
----

The distinction is semantic rather than syntactic.


=== Separate Engine and API Services

Development shall assume two independently supervised production processes:

[source,text]
----
aquaponics-engine
aquaponics-api
----

The Engine is primary.

The API is optional from the perspective of physical control.

Development shall verify that:

* Engine startup does not require API startup;
* API failure does not stop Engine execution;
* API restart does not stop Engine execution;
* Engine restart is independently recoverable;
* API detects Engine unavailability;
* API reconnects or recovers after Engine availability returns.

The API shall never become part of the physical life-support control loop.


=== Production Dependency Direction

The runtime dependency direction is:

[source,text]
----
Web / Mobile / SHMC / AI / external clients
                  |
                  v
                 API
                  |
                  | local IPC
                  v
                Engine
                  |
                  v
        physical control system
----

The API depends on the Engine for authoritative control semantics.

The Engine shall not depend on API availability.


=== IPC Development Boundary

API-to-Engine communication shall use a defined local IPC abstraction.

The first concrete transport may be selected in a dedicated implementation issue.

A Unix domain socket is a preferred candidate for a single-machine production installation.

Other suitable local IPC mechanisms may be used where justified.

Application code shall not make domain semantics depend on the selected transport.

Changing IPC implementation shall not require redesigning:

* command semantics;
* command lifecycle;
* scheduling;
* autonomous policies;
* persistence rules;
* actuator semantics.

Tests should be able to replace transport details without replacing Engine behaviour.


=== External-Ingress Processing

External communication shall be processed by the Engine without becoming the driver of the Engine.

Engine ingress shall be:

* non-blocking; or
* explicitly time-bounded.

A stalled external connection shall not indefinitely stop:

* sensor acquisition;
* state reconciliation;
* schedule processing;
* autonomous-policy evaluation;
* command execution;
* persistence;
* health reporting.

Each control cycle may process:

* a bounded number of incoming requests; or
* a bounded amount of ingress-processing time.

Additional work may remain queued for later cycles.


=== External-Ingress and Backlog Tests

Tests shall verify that:

* a client that connects and then stops responding does not freeze the Engine;
* malformed requests do not stop autonomous operation;
* excessive external traffic does not indefinitely starve the control loop;
* a large pending-command backlog does not indefinitely prevent sensor processing;
* API failure does not stop Engine operation;
* IPC failure does not stop local autonomous control.

The central invariant is:

[IMPORTANT]
====
External communication is serviced by the Engine.

External communication does not drive the Engine.
====


=== Command Processing Bounds

Command execution shall not monopolize the control loop indefinitely.

Where necessary, command processing shall use bounded:

* work count;
* execution time;
* batch size.

Long-running physical operations should generally be represented through state rather than by blocking the entire Engine until completion.

For example:

[source,text]
----
bad:

pump_on()
sleep(300)
pump_off()
----

should normally be represented conceptually as:

[source,text]
----
command starts pump
       |
       v
state records active operation
       |
       v
normal Engine cycles continue
       |
       v
later due transition stops pump
----

Exact implementation shall follow domain requirements.


=== Command Ordering

When multiple commands are eligible for execution, ordering shall be deterministic.

Execution shall not depend accidentally on:

* database row order;
* thread scheduling;
* socket arrival timing;
* process scheduling;
* Python container ordering.

The command model shall support explicit ordering information where required.

Possible inputs include:

* command priority;
* intended execution time;
* acceptance sequence;
* command identifier.

The exact priority model shall be introduced deliberately and tested.


=== Command Idempotency

Commands that may be retried across process or communication failure shall have deliberate idempotency semantics.

A single logical operation shall not execute multiple times merely because:

* an API client retried;
* the IPC connection failed after submission;
* the response was lost;
* the Engine restarted;
* schedule evaluation occurred repeatedly.

Where required, commands shall carry:

* stable command identity;
* occurrence identity;
* idempotency key;
* equivalent deterministic identity information.


=== Command Acceptance Tests

State-changing command tests shall distinguish:

* request received by API;
* intent received by Engine;
* command validated;
* command durably accepted;
* command execution started;
* command execution completed or failed.

A successful HTTP response from a transport layer shall not by itself prove Engine acceptance.


=== Command Ordering and Idempotency Tests

Tests shall verify deterministic behaviour when multiple commands become eligible for execution.

Where applicable, tests shall cover:

* equal-time commands;
* different priorities;
* retries;
* duplicate submission;

=== Running the Engine in Development

The current Engine is a development foundation, not a production controller.

It provides a continuously repeating operating cycle, a local administrative IPC interface, a lifecycle audit history, and controlled shutdown.
Each operating cycle passes through the seven phases described in "Operating-Cycle Phases" in the architecture chapter.
Only `INGEST_EXTERNAL_INTENTS`, which services administrative requests, does any work; the other phases are placeholders that do nothing.
It does not provide:

* hardware, GPIO or relay control;
* sensors, scheduling or environmental control;
* the durable operational command journal or any operational state database;
* state reconciliation after a restart;
* a REST API;
* an installed production service: the reviewed `systemd` unit exists and can be installed manually (see "Engine Service (Initial Implementation)"), but it is not installed on the controller.

It must not be composed with real hardware adapters in this form.

Install the package in a virtual environment (see the repository `README.md`).
The commands `aquaponics-engine` and `ape` are installed with the package;
`python -m aquaponics_controller.engine_main` and `python -m aquaponics_controller.cli` are equivalent.

Starting the Engine in one terminal:

[source,text]
----
$ aquaponics-engine
----

Checking from a second terminal that the Engine is running and processing requests:

[source,text]
----
$ ape --ping
pong: the Engine is reachable (execution 6f1c...e2, pid 12345)
operating cycles completed: 42
Engine time: 2026-11-12T06:21:26.655626Z

$ ape --echo "hello Engine"
hello Engine
----

`ape --ping` and `ape --echo TEXT` are stateless diagnostic queries (see "Request Classes").
The answer is produced by the running Engine, not by `ape`: the execution identifier, process identifier, cycle count and time in a `ping` answer are the Engine's own.
`TEXT` is limited to 256 characters.
The limit counts Unicode characters, not bytes, and is enforced by the Engine.
A text that starts with `-` must be written as `--echo=-text`.
Neither query changes anything, and neither is recorded in the lifecycle audit history.

Requesting a controlled shutdown from a second terminal:

[source,text]
----
$ ape -x
Engine shutdown initiated. This does not confirm that the Engine process has exited.
----

Exactly one of `-x`, `--ping` and `--echo` is chosen per invocation.

The Engine options are:

[cols="2,5",options="header"]
|===
|Option |Meaning

|`--socket PATH`
|Administrative IPC endpoint. See "Local Administrative IPC (Initial Implementation)".

|`--audit-file PATH`
|Lifecycle audit file. See "Lifecycle Audit Persistence".

|`--cycle-interval SECONDS`
|Operating cycle interval, between 0.01 and 60 seconds. The default is 1.0.

|`--log-level LEVEL`
|`DEBUG`, `INFO` (default), `WARNING` or `ERROR`. Diagnostic logs always go to standard error. See "Diagnostic Logging (Initial Implementation)".

|`--log-file PATH`
|Also write diagnostic logs to this size-rotated file, bounded to 25 MiB in total. Not set by default. See "Diagnostic Logging (Initial Implementation)".
|===

The Engine services administrative requests during each operating cycle and also while it idles between cycles.
A request, and a shutdown request in particular, is therefore answered promptly even with a long cycle interval, and does not start an additional operating cycle.
The remaining delay is the duration of an operating cycle already in progress, plus the bounded time (see "Bounds") spent servicing requests.
The `ape` default timeout of five seconds is unchanged.

Phase time limits:: Each phase has a time limit, defined as a code constant in `cycle_phases.py`, not as an option: 0.9 seconds for `INGEST_EXTERNAL_INTENTS` (the ingress bounds below: 0.5 s of servicing plus one connection's read and write deadlines) and 0.1 seconds for each placeholder phase, 1.5 seconds per cycle in total.
The limits are cooperative: a running phase is not interrupted.
A phase that took longer than its limit is logged as a `WARNING` naming the phase, the elapsed time and the limit, and the Engine continues.
Overruns of a phase that stays slow are subject to repeat suppression (category `phase-overrun:<PHASE>`, see "Diagnostic Logging (Initial Implementation)").
An overrun is not a lifecycle audit event.
A cycle that took longer than the cycle interval is followed immediately by the next one; missed cycles are not caught up.
A phase that blocks indefinitely is not detected by the Engine itself. Under the service, the systemd watchdog detects it, because no heartbeat follows (see "Engine Service (Initial Implementation)").

A shutdown request or a handled signal received during a cycle lets that cycle finish all its phases; no further cycle starts.
Requests answered while the Engine idles run no phase.

Idle servicing uses one thread and one loop.
The idle wait ends when the cycle deadline is reached, when the IPC socket reports a waiting client, or when a stop is requested (including by `SIGINT` and `SIGTERM`).
It costs no CPU while nothing happens.
If the socket reports a waiting client but no request can be serviced, for example because the process has run out of file descriptors, the Engine ignores the socket for 0.25 seconds before listening again, so that it cannot spin.

Ways in which an Engine execution ends:

[cols="2,3,1",options="header"]
|===
|Cause |Behaviour |Exit status

|Operator request (`ape -x`)
|Lifecycle-control request (see "Lifecycle-Control Requests"). Controlled shutdown, cleanup.
|0

|`SIGINT` (Ctrl+C) or `SIGTERM`
|Best-effort controlled shutdown, cleanup. Recorded as an external interruption by that signal.
A handled signal does not establish that an operator authorized the interruption.
It is not interpreted as an administrative request.
|0

|Unexpected Python exception
|Logged with its traceback, cleanup attempted, never suppressed.
An exception in an operating-cycle phase ends that cycle: its remaining phases do not run and it is not counted.
|1

|Command-line or configuration error, including a cycle interval too long for the service watchdog or a malformed service-manager variable
|Reported on standard error. The Engine does not start.
|2

|Another Engine already owns the endpoint
|Reported. The running Engine is not disturbed.
|3

|Shutdown carried out, but cleanup reported an error
|Logged.
|4

|`SIGKILL`, power loss
|No cleanup and no final audit events are possible. Recovery after such an interruption is outside this implementation.
|(none)

|Other signals, for example `SIGHUP` when a terminal is closed
|Not supported: the default action ends the process without cleanup, like `SIGKILL`. The stale endpoint is replaced at the next start. Under the service, a death by `SIGHUP` is restarted (`RestartForceExitStatus=SIGHUP`).
|(set by the signal)
|===

Only `SIGINT` and `SIGTERM` are supported.
The first stop reason wins: a repeated signal, or a signal after an operator STOP, changes nothing and is not recorded again.
A shutdown that blocks (for example on storage) is not shortened by another signal; escalation is `SIGKILL`, which the service manager sends after its 10-second stop timeout (`TimeoutStopSec`).

Exit status 0 after a handled signal reports that the shutdown completed, not who requested it.
The service treats it as a deliberate stop and does not restart the Engine; it is not proof of operator authorization.

The `ape` client reports through its exit status:

[cols="1,5",options="header"]
|===
|Status |Meaning

|0 |The Engine answered successfully. For `-x` this confirms that shutdown was initiated, not that the process has exited.
|1 |The Engine refused the request (for example invalid arguments or an unsupported operation).
|2 |Usage or configuration error.
|3 |The Engine is not reachable: the endpoint does not exist, or nothing is listening.
|4 |Permission denied: by the operating system, or by the Engine (`peer_not_authorized`: the connecting Linux user is not authorized for administration).
|5 |No answer within the timeout (`--timeout`, default 5 seconds). This includes an Engine that stayed busy: its connection queue was full until the timeout.
|6 |The connection failed or the answer was not understood. This includes a connection that was closed without an answer (the request was *not acknowledged*, for example because the Engine was shutting down) and an `internal_error` answer (the Engine failed while handling the request and is stopping).
|===

`ape` never sends a process signal and never resends a request.
It only retries *establishing the connection* while the Engine's connection queue is full; nothing has been sent at that point (see "Lifecycle and IPC Failure Handling").

=== Local Administrative IPC (Initial Implementation)

This section documents the first concrete local IPC mechanism, as required by "Local IPC Deployment".
It is an initial implementation for the administrative interface only.
The wire protocol is not a general command framework.

Transport:: A Unix domain socket (`AF_UNIX`, stream), using only the Python standard library.
No network, Internet or external IPC dependency is involved.

Endpoint path:: Configurable. The first available of: `--socket PATH`, the environment variable `AQUAPONICS_ENGINE_SOCKET`, `$XDG_RUNTIME_DIR/aquaponics/engine.sock`.
If none is available, the Engine and `ape` report a configuration error.
Unix socket paths are limited to about 107 bytes.
The production location (for example under `/run/aquaponics/`) is not decided here.

[cols="1,4",options="header"]
|===
|Deployment item |Initial implementation

|Path
|As above. Configurable.

|Owner
|The user running the Engine.

|Group
|The primary group of the Engine's user. No group access is granted by default.

|Permissions
|The endpoint's directory is created with mode `0700` and the socket with mode `0600`, independent of the process umask.
An existing directory is validated before use (see "Directory validation" below).

|Creation
|By the Engine at startup.

|Cleanup
|By the Engine during shutdown. The socket is removed only if it is still the one this Engine created.
A socket left behind by `SIGKILL` or a crash is stale and is replaced at the next start.
Something at the endpoint path that is not a socket, or a socket owned by another user, is never removed.

|Restart behaviour
|A restarted Engine acquires the endpoint without manual intervention.
|===

Single instance:: The Engine holds an exclusive `flock` on `<endpoint>.lock` for as long as it runs.
A second Engine on the same endpoint fails to start (exit status 3) without disturbing the first.
The kernel releases the lock when the process ends, including after a crash.
The lock file is never deleted, because deleting lock files races with a starting Engine.
The lock file is opened without following a symbolic link and must be a regular file owned by the Engine's user.

Directory validation:: Only the endpoint's immediate directory is examined or changed, never its parents.
It is opened without following a symbolic link, and every check, and the one permitted correction, is made on that open directory, so the directory checked is the directory changed.
+
[cols="2,3",options="header"]
|===
|Condition |Behaviour

|Missing |Created with mode `0700`. Parent directories that have to be created as well keep the default mode.
|A symbolic link (even one pointing to a suitable directory) |Refused. The link and its target are left alone.
|Not a directory |Refused.
|Not owned by the Engine's user |Refused.
|Writable by group or others |Refused: its content may already have been manipulated, so it is not repaired.
|Only readable or searchable by group or others |Restricted to `0700`, with a `WARNING` naming the previous mode.
|===
+
A refusal stops startup: the Engine logs the reason, records `ENGINE_FAILURE` (phase `startup`) and exits with status 1.
Nothing is created, removed or changed in the directory, and no lock is held.
There is no fallback endpoint, because clients could not find it.
Someone who can write to the directory's *parent* could still exchange the directory between the check and the creation of the socket; choosing a safe location is the operator's responsibility (the default, `$XDG_RUNTIME_DIR`, is a `0700` directory owned by the user).

Access control::
* Linux filesystem permissions decide who can connect. By default only the Engine's user (and root) can.
* The Engine reads the kernel-reported credentials of the connecting process (`SO_PEERCRED`) and, as Engine-side enforcement, accepts administrative operations only from users in its configured administrative set. The default set is the Engine's own user and root. A peer whose credentials cannot be read is refused.
* The credentials (uid, gid, pid) are recorded in the lifecycle audit history. A pid can be reused and is informational.
* No Aquaponics-specific login or password exists.
* Granting access to a dedicated administrative group is a deployment decision for later work. It requires changing both the directory/socket permissions and the Engine's administrative user set.
* The future REST API is a separate Linux service identity (see "Authentication and Authorization"). It shall not receive access to this administrative interface merely because the Engine's interface exists. A separate, differently permissioned endpoint is the expected approach.

Request format:: One request and one response per connection, each a single newline-terminated UTF-8 JSON object of at most 4096 bytes.
The protocol version remains 1. The fields below were added without changing the existing ones.
For example `{"v": 1, "op": "echo", "submitted_at": "2026-11-12T06:00:00+00:00", "id": "7f3a...", "args": {"text": "hello"}}`.

[cols="1,4",options="header"]
|===
|Field |Meaning

|`v` |Protocol version. Must be 1.
|`op` |Operation name: `ping`, `echo` or `stop`.
|`submitted_at` |Optional. A timezone-aware time reported by the client. Informational only.
|`id` |Optional correlation identifier, a string of 1 to 64 characters. The answer repeats it. It is not a durable command identifier and not an idempotency key. `ape` generates a new one for every request and rejects an answer that does not repeat it.
|`args` |Optional argument object. Its content is validated by the Engine for each operation.
|===

Operations:: All three need the authorization described under "Access control".
* `ping`: a query. No arguments. The answer's `result` is `{"reply": "pong", "execution_id": ..., "engine_pid": ..., "cycles_completed": ..., "engine_time_utc": ...}`. `cycles_completed` counts completed operating cycles; a cycle in progress is not counted.
* `echo`: a query. Exactly one argument, `text`, a string of at most 256 characters (Unicode characters, not bytes) that can be encoded as UTF-8 (an unpaired surrogate is refused). The answer's `result` is `{"text": ...}`. The largest valid request and answer fit in the 4096-byte limit even when every character needs a 12-byte JSON escape.
* `stop`: a lifecycle-control request. No arguments.

Responses:: `{"v": 1, "ok": true, "id": "...", "result": {...}}` for a query, `{"v": 1, "ok": true, "status": "shutdown_initiated", "id": "..."}` for `stop`, and `{"v": 1, "ok": false, "error": "<code>", "message": "<text>", "id": "..."}` for a refusal.
The `id` is present when the request carried a valid one.
A refusal never repeats the rejected text.

Error codes::
[cols="2,4",options="header"]
|===
|Code |Meaning

|`malformed_request` |Not valid UTF-8 JSON, not a JSON object, or a field has the wrong type.
|`unsupported_protocol_version` |`v` is not 1.
|`request_too_large` |More than 4096 bytes.
|`request_timeout` |The request line did not arrive in time.
|`invalid_correlation_id` |`id` is not a string of 1 to 64 characters.
|`invalid_arguments` |`args` is not an object, or its content is not valid for the operation (missing, unexpected or wrongly typed argument, text longer than 256 characters).
|`unsupported_operation` |`op` is not one of the supported operations.
|`peer_not_authorized` |The connecting Linux user is not authorized for administration.
|`internal_error` |Not a refusal: handling the request failed inside the Engine, which is now stopping (see "Failure classification"). Fixed text; it never contains exception details.
|===

None of the refusals stops the Engine. `ape` reports `peer_not_authorized` with exit status 4, `internal_error` with exit status 6, and every other refusal with exit status 1.

Bounds:: Per call the Engine accepts at most 8 connections, spends at most 0.2 s waiting for each request line, and at most 0.5 s in total.
A call is made in every operating cycle, and again whenever the IPC socket reports a waiting client while the Engine idles.
While idling, the time spent is also limited to the time left before the next cycle is due, and at least one waiting connection is handled per call.
A stalled or malicious local client can therefore delay a cycle by a bounded time (about one connection's read and write deadlines, at most 0.4 s), never indefinitely.
The listen backlog is 8. Clients beyond it cannot connect until the Engine accepts queued ones; they never block the Engine.
`ape` then retries connecting, and only connecting, until its timeout (see "Lifecycle and IPC Failure Handling").
`ape` bounds the entire exchange with one overall deadline, its timeout.

Diagnostic traces:: For every request that is read, the Engine logs (at `INFO`) that it was received, that it was processed, and that it was answered, naming the operation, the correlation identifier and the outcome.
The identifier is client-supplied text and is logged quoted.
The arguments, in particular the `echo` text, are never logged.
Refused requests are traced the same way, with the error code.
Every trace line also carries the Engine execution identifier and the cycle field (see "Diagnostic Logging (Initial Implementation)"), so a request can be followed from receipt to answer within one execution.

Acknowledgement:: `shutdown_initiated` means the Engine has decided to shut down.
A `ping` or `echo` answer reports a result; it does not mean anything was accepted for later execution.
It does not mean the Engine process has exited.
A repeated request during shutdown receives `shutdown_already_initiated`, if it is still served (see "Shutdown servicing").
The word "accepted" is deliberately not used: it is reserved for durable acceptance of operational commands (see "Engine Ingress").

Manual verification of cross-user denial:: Automated tests cannot assume a second Linux account.
To verify it by hand, with the Engine running as user A and a second account B:

[source,text]
----
$ sudo -u B ape -x --socket /path/to/engine.sock
ape: permission denied for /path/to/engine.sock        (exit status 4)
----

The Engine must keep running, and its lifecycle audit history must contain no `STOP_REQUEST_RECEIVED` for the attempt.

=== Lifecycle and IPC Failure Handling

This section defines how the Engine and `ape` behave when things go wrong around the local administrative IPC and the Engine lifecycle (Issue #8).

Nominal responsiveness targets:: These are *nominal targets, not guarantees*.
While writing the lifecycle audit history (`fsync`) and synchronous diagnostic logging can block (see "Diagnostic Logging (Initial Implementation)"), they are not hard real-time guarantees, and they are not documented or tested as such.
+
* A STOP is acknowledged within about 1 second, provided the Engine's connection queue is not saturated.
* After an acknowledged STOP or a handled `SIGINT`/`SIGTERM`, the process exits within about 2 seconds, whatever the cycle interval.
+
The worst case follows from the existing bounds: the rest of a cycle's request servicing if the stop arrives during it (up to 0.9 s), the remaining placeholder phases (about 0 s), the final servicing pass (up to 0.25 s plus one connection's 0.4 s), and cleanup: about 1.6 s.
A typical shutdown takes well under 0.1 s.
The tests use 5 seconds as their tolerance.

Shutdown servicing:: A controlled shutdown (operator STOP or handled signal) proceeds in this order:
+
. `SHUTDOWN_INITIATED` is recorded.
. *The endpoint is withdrawn.* The socket path is removed (only if it is still the socket this Engine created). A client that tries to connect from now on finds no endpoint (`ape` exit status 3). The listener and the instance lock stay held.
. *One final servicing pass.* The clients already queued are served once, through the normal path with its usual limits (at most 8 connections, 0.2 s to read and 0.2 s to write each) and its authorization rules, for at most 0.25 s. It never waits for new clients. A STOP is answered `shutdown_already_initiated` and audited as `STOP_REQUEST_RECEIVED` with `shutdown_already_initiated: true`; that record appears between `SHUTDOWN_INITIATED` and `SHUTDOWN_COMPLETED`. A query is answered as usual.
. The listener is closed, the lock released, cleanup completed and `SHUTDOWN_COMPLETED` recorded, as before.
+
*No answer is promised to every queued client.* Clients beyond the pass's limits, or still queued when the listener closes, get no answer: their connection is reset. Shutdown is never extended to drain the queue.
After an Engine failure there is no final pass: the shutdown goes straight to cleanup.
An unexpected exception during the final pass is an Engine failure like any other: the client being served receives `internal_error` (best effort), `ENGINE_FAILURE` is recorded with phase `shutdown`, cleanup still runs exactly once, and the exit status is 1 (`SHUTDOWN_COMPLETED` keeps the reason that started the shutdown and records exit status 1).
+
*Acknowledged and lost requests.* A STOP is acknowledged only if the client received an answer (`shutdown_initiated` or `shutdown_already_initiated`). The answer confirms that the Engine received the request and has initiated shutdown, or had already initiated it. It also reports, in `audit_recorded`, whether the Engine could persist the request's `STOP_REQUEST_RECEIVED` record: writing the lifecycle audit history can fail, and the Engine then still answers and shuts down, with `audit_recorded: false` (`ape` prints a warning). A persisted audit record is therefore not guaranteed for every acknowledged STOP. A request that got no answer was *not acknowledged* and must be treated as lost: the client cannot tell whether it was read.
+
[cols="3,3",options="header"]
|===
|Engine state when the client connects |`ape` result

|Running |Normal answer (exit status 0, 1 or 4).
|Running, connection queue full |Retries connecting until its timeout, then exit status 5, "the Engine is busy".
|Shutting down; the client was already queued and is served in the final pass |STOP: exit status 0, "already initiated". Queries: answered as usual.
|Shutting down; the client was queued but not served |Exit status 6, "the request was not acknowledged".
|Shutting down; the endpoint was already withdrawn |Exit status 3, "no Engine is listening" (the process may still be finishing cleanup).
|Exited, or killed (a stale socket remains) |Exit status 3.
|===

Failure classification:: Three classes, kept strictly apart:
+
. *Per-connection failures*: logged as a `WARNING`; that connection is closed and the Engine continues. They are not audited, like a client disconnect. Only these errors, raised by an operation on the accepted client connection itself (`recv`, `sendall`, `settimeout`, `getsockopt` or `close`), belong here:
** the client went away: `ECONNRESET`, `EPIPE`, `ECONNABORTED`, `ENOTCONN`;
** the connection's own read or write deadline expired (`TimeoutError`);
** a transient shortage of kernel resources on that socket: `ENOBUFS`, `ENOMEM`, `EAGAIN`/`EWOULDBLOCK`.
+
Any other `OSError`, even from those operations (for example `EBADF`, `EINVAL`, `ENOTSOCK`), indicates a defect and is *not* contained. The classification is one named constant in `local_ingress.py`, checked by the tests.
. *Protocol refusals*: answered with their error code and logged; the Engine continues (see "Local Administrative IPC (Initial Implementation)").
. *Engine failures*: everything else, including any exception from the request handler (also an `OSError` raised by Engine code), any decoding error other than a protocol error, and any exception from the operating-cycle phases. The Engine stops (fail-stop): `ENGINE_FAILURE` is recorded, cleanup is attempted once, and the exit status is 1. Nothing about this has changed.
+
*`internal_error` answer.* When the request handler raises, the client is first sent one fixed answer, as a courtesy: `{"ok": false, "error": "internal_error", "message": "the Engine encountered an internal error and is stopping"}`, with the request's `id` if it had one.
It is a single attempt within the usual 0.2 s write deadline, it never contains the exception's type, text or traceback, and a failure to send it never replaces the original exception, which then takes the fail-stop path unchanged.
The exception details go only to the diagnostic log (as an `ERROR` with traceback) and to the `ENGINE_FAILURE` record (exception type and message), as before.
Interruptions (`KeyboardInterrupt`, `SystemExit`) are never turned into an answer.
`accept()` failures on the listening socket follow the same principle (Issue #9, D14). Only these are contained: descriptor or memory exhaustion (`EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`) and a client that went away while queued (`ECONNABORTED`). For them nothing has changed: no further connections in that call, the 0.25 s idle backoff, and repeat suppression by category. An empty queue (`EAGAIN`) is not an error. *Any other `accept()` error* (for example `EBADF`, `EINVAL`, `ENOTSOCK`) means the listener itself is broken: it is an Engine failure (fail-stop, exit status 1), and under the service the Engine is restarted with a fresh endpoint, instead of carrying on, heartbeat included, without administrative access. The set is the named constant `CONTAINED_ACCEPT_ERRNOS` in `local_ingress.py`, checked by the tests.

Connecting while the Engine is busy:: A Unix socket does not make a client wait for room in a full connection queue: connecting fails at once (`EAGAIN`).
`ape` treats this as "the Engine is alive but busy" and retries *connecting only*, with a short backoff (10 ms, doubling up to 100 ms), until its timeout; then it exits with status 5.
Nothing has been sent at that point, so this cannot duplicate a request.
Once connected, the request is sent exactly once and is never resent, whatever happens afterwards.
One overall deadline, the `--timeout`, covers connecting, sending and waiting for the answer.
A missing endpoint or nothing listening is reported at once with exit status 3, a permission problem with exit status 4; neither is retried.

Duplicate requests:: The correlation identifier is not an idempotency key, and the Engine does not deduplicate requests.
Queries (`ping`, `echo`) are safe to repeat.
A STOP repeated within one Engine execution is idempotent: it is answered `shutdown_already_initiated` and audited each time, without a second shutdown.
A STOP sent after the Engine has been restarted is a new STOP for the new execution. Stopping only a specific execution is not supported (future work). Under the service, a STOP is never undone by an automatic restart.

Descriptor exhaustion:: If the Engine runs out of file descriptors (or kernel memory) while accepting a connection, it stops accepting for that call, ignores the socket for 0.25 s while idle so that it cannot spin, and logs the condition under its repeat-suppression category.
Waiting clients stay queued and are served automatically once the condition clears.
While the condition lasts, the Engine keeps completing operating cycles and sending its service heartbeat: the heartbeat does not cover IPC availability (see "Known Limitations" under "Engine Service (Initial Implementation)").

=== Diagnostic Logging (Initial Implementation)

Diagnostic logs describe what the Engine software did, for investigation.
They are not authoritative: they are not the lifecycle audit history (see "Lifecycle Audit Persistence"), not the durable command journal and not state history, and nothing reads them to decide what to do.
The implementation is `aquaponics_controller.diagnostic_logging`; it uses the Python standard library `logging` package, configured once per process by the Engine entry point.

Format:: One text line per record:
+
[source,text]
----
2026-11-12T10:00:49.917Z INFO engine exec=6f1c...e2 cycle=42 IPC request processed by the Engine: op='ping' id='a1' outcome=ok
----
+
The fields are: the UTC time with milliseconds; the level; the subsystem (the module name without the `aquaponics_controller.` prefix); `exec=`, the Engine execution identifier; `cycle=`, the number of the operating cycle in progress, or `-` outside a cycle (startup, requests answered while idling, shutdown); the message.
A traceback, where present, follows on further lines.
The timestamp comes from the logging framework and is informational; durations within messages are measured with the monotonic clock.

Correlation:: The execution identifier is generated once by the entry point, before anything is logged, and the same value is given to diagnostic logging, the lifecycle audit history and the Engine.
Every record of one execution carries it, so a log line can be matched to the execution's audit records.
The cycle number is fixed at the start of each cycle.
A failure raised inside a cycle is logged with that cycle's number, the same number the `ENGINE_FAILURE` audit record contains; records of the subsequent shutdown carry `cycle=-`.
Requests are traced by their correlation identifier (see "Diagnostic traces" above).

Levels:: As described in "Logging Levels" in the AI Code and Logic Guidelines.
The default is `INFO`.
Idle operating cycles log only at `DEBUG` (one record per cycle), so an idle Engine produces no `INFO` output.
An Engine failure is logged at `ERROR` with its traceback.
`CRITICAL` is not used while the Engine has no physical responsibilities.

Destinations and storage:: Two destinations, with different storage guarantees:
+
* Standard error, always. The Engine does not bound what is kept: that depends on whatever captures standard error. A terminal keeps nothing; redirecting standard error to a file in the shell gives an *unbounded* file and is not recommended; under `systemd`, journald keeps it according to its own configuration (persistence, size and rate limits), which belongs to the service setup. When standard error is the journald stream, every line carries its syslog priority prefix (`<3>` error, `<4>` warning, `<6>` info, `<7>` debug), so that `journalctl -p` selects by severity; elsewhere lines are unchanged (see "Journal" under "Engine Service (Initial Implementation)").
* The file given with `--log-file PATH`, optionally. The Engine bounds it: it is rotated at 5 MiB, and 4 rotated files are kept (`PATH.1` to `PATH.4`), at most 25 MiB in total. Sizes are counted in bytes. Only a single record larger than 5 MiB, written to an empty file, can make a file larger. If rotation fails, the record is dropped instead of appended beyond the limit. The directory is created with mode `0700` if it does not exist; an existing directory, and every parent directory, is left as it is. The file is created with mode `0600`. The file is opened safely, at startup and after every rotation: a symbolic link at the file's path is not followed; only a regular file with a single name is accepted (a named pipe, a device or a directory is refused, without blocking, and so is a file with more than one hard link, before anything about it is changed); an existing file with other permissions is restricted to `0600` with a warning, and refused if that is not permitted (for example because it belongs to another user). The file is not `fsync`-ed: recent lines can be lost on power loss.
+
No remote or external logging service is used.

Repeat suppression:: Only explicitly chosen, known, repetitive and low-information warnings are subject to repeat suppression, each under its own predefined category:
+
[cols="2,5",options="header"]
|===
|Category |Warning

|`ipc-accept-failed:EMFILE`, `ipc-accept-failed:ENFILE`, `ipc-accept-failed:ENOBUFS`, `ipc-accept-failed:ENOMEM`
|Accepting an IPC connection failed because of descriptor or memory exhaustion. While the condition lasts this can recur every 0.25 seconds. An `accept()` failure with any other error is always logged.

|`ingress-budget-exhausted`
|The ingress time budget was used up with clients still waiting.

|`phase-overrun:<PHASE>`, one per operating-cycle phase
|An operating-cycle phase exceeded its time limit.
|===
+
Within a window of 300 seconds from the first logged occurrence, the first 3 occurrences of a category are logged (the third says that further repeats are counted); later ones are only counted.
The next occurrence after the window has ended is preceded by one summary, for example `... 412 similar warnings suppressed in 300 s (category ipc-accept-failed:EMFILE; last: [Errno 24] Too many open files)`, and starts a new window.
Pending summaries are written during shutdown.
Each category keeps only counters and one sanitized description of the last suppressed occurrence (control characters escaped, at most 200 characters); no exception objects or message arguments are kept.
Nothing else is suppressed: errors, lifecycle transitions, Engine failures, refused requests (unauthorized peers, malformed or unsupported requests), client disconnects, lifecycle audit failures and cleanup failures are always logged.

Failure of a log destination:: A destination that cannot be written to never raises an error into the Engine and never stops it.
Its first failure is reported once, as one line written directly to standard error (file descriptor 2), not through the logging system:
+
[source,text]
----
aquaponics-engine: diagnostic log handler log-file failed (OSError, errno 28); further failures are counted
----
+
The report names only the destination, the exception type and the error number; it contains no traceback and nothing of the record being written.
Later failures are counted, each new record is attempted again, and during shutdown the number of records that could not be written is logged through the remaining destinations.
If the `--log-file` cannot be opened or is refused as unsafe at startup, a warning is written to standard error and the Engine runs with standard error only: a problem with diagnostic logging does not prevent the Engine from starting.
If the file cannot be reopened safely after a rotation, records are dropped and counted as for any other failure of the destination.

Never logged:: Request arguments (in particular the `echo` text), credentials and raw request bytes.
Client-supplied identifiers are logged quoted.
Signal handlers do not log: they only set the stop flag and wake the idle wait.

Synchronous logging limitation:: Logging is synchronous; no thread or process writes logs on the Engine's behalf.
The time spent writing a record is therefore not strictly bounded: a reader of standard error that stops reading (a full pipe, a paused terminal, a stalled journald) or slow or failing storage can block the Engine thread, and while it is blocked nothing else happens, including request handling and the operating-cycle schedule.
In-process phase timing cannot detect this; under the service, a block longer than the watchdog timeout ends in a watchdog restart.
*This limitation must be resolved before physical equipment control is enabled* (see "Logging" in the architecture chapter).

=== Lifecycle Audit Persistence

Every Engine execution appends records to a lifecycle audit file, as required by "Engine Lifecycle Audit History".

File location:: The first available of: `--audit-file PATH`, the environment variable `AQUAPONICS_LIFECYCLE_AUDIT_FILE`, `$XDG_STATE_HOME/aquaponics/lifecycle_audit.jsonl` (default `~/.local/state/aquaponics/lifecycle_audit.jsonl`).
The directory is created with mode `0700` and the file with mode `0600`.
The production location is not decided here.

Format:: JSON Lines: one JSON object per line, appended, never rewritten.
Records contain: `format`, `timestamp_utc` (absolute UTC), `execution_id` (unique per Engine execution), `sequence` (within the execution), `event`, `reason`, `requester` (uid, gid, pid, where applicable) and `context`.

Events:

[cols="2,5",options="header"]
|===
|Event |Meaning

|`ENGINE_STARTING` |Startup began. Context includes the Engine pid, endpoint and audit file.
|`ENGINE_RUNNING` |Startup completed. The Engine enters continuous operation.
|`STOP_REQUEST_RECEIVED` |An authorized operator STOP request was received through the administrative IPC. The record's timestamp and `engine_receipt_time_utc` are the Engine's authoritative receipt time. `client_reported_submission_time_utc` is what the client claimed, and is informational.
|`SHUTDOWN_INITIATED` |Shutdown began. `reason` is `OPERATOR_STOP`, `SIGNAL` (context names the signal) or `FAILURE`.
|`SHUTDOWN_COMPLETED` |Cleanup finished. Context reports whether cleanup succeeded, the exit status and the number of cycles.
|`ENGINE_FAILURE` |A failure was detected. `reason` is the exception type; context names the lifecycle phase in `phase` (`startup` or `operation`). If the failure occurred inside an operating-cycle phase, context also contains `cycle_phase` (for example `RECONCILE_STATE`) and `cycle_number` (the cycle in progress, counting from 1). A failure outside every cycle phase, for example while answering a request between cycles, has neither field.
|===

Refused requests (unauthorized peers, malformed or unsupported requests) and the diagnostic queries `ping` and `echo` are logged diagnostically and are not lifecycle audit events.

Example sequence for an operator shutdown: `ENGINE_STARTING`, `ENGINE_RUNNING`, `STOP_REQUEST_RECEIVED`, `SHUTDOWN_INITIATED`, `SHUTDOWN_COMPLETED`.

Reading:: The file is plain text, for example `jq . lifecycle_audit.jsonl`.
`aquaponics_controller.lifecycle_audit.read_lifecycle_records` reads it for tests and inspection and skips a partly written final line.
Nothing in the Engine reads the file at startup or at any other time to decide what to do.
Records are evidence. A `STOP_REQUEST_RECEIVED` or `SHUTDOWN_INITIATED` record from an earlier execution has no effect on a later one.

Durability and its limits::
* Each record is written with one `write` to a file opened in append mode and is followed by `fsync`. The directory is `fsync`-ed when the file is first created.
* A record is therefore on stable storage when `record` returns, as far as the operating system and the storage device honour `fsync`. Devices or filesystems that acknowledge writes they have not made durable can still lose records on power loss.
* `fsync` has no timeout. A failing disk can block the Engine in `fsync`; this implementation does not bound that, because it would require threads or a separate process.
* After `SIGKILL`, a crash or power loss the final events (`SHUTDOWN_INITIATED`, `SHUTDOWN_COMPLETED`) are absent, and the last line may be incomplete. This implementation does not detect or mark an unclean previous execution; that belongs to later recovery development.
* A second Engine refused because the endpoint is in use still records its own `ENGINE_STARTING`, `ENGINE_FAILURE`, `SHUTDOWN_INITIATED` and `SHUTDOWN_COMPLETED` under its own execution identifier. Its records are appended as whole lines.
* There is no rotation, retention or size limit. Bounded retention is a later concern (see "Disk Protection").
* If the file cannot be opened at startup, the Engine does not start (exit status 1), because an execution without an audit history is not permitted.
* If a record cannot be written later, an `ERROR` is logged ("LIFECYCLE AUDIT RECORD NOT PERSISTED"), `ape` prints a warning where the request was affected, and shutdown and cleanup continue.

Lifecycle audit history is not a diagnostic log (see "Logging"), not the durable command journal, and not a source of pending work.

Administrative access:: The IPC directory belongs to `aquaponics` and is `0700`.

`ape` is installed only in the service's virtual environment, and `sudo` searches only its own fixed path (`secure_path`), so `ape` is always called by its absolute path `/opt/aquaponics/venv/bin/ape`.
An administrative group is future work.
`systemctl` remains an administrative path that does not depend on the IPC endpoint.

==== Installation

On a non-production workstation, or on the controller when installation there has been authorized.
Run from a checkout of the reviewed release, with that release's commit checked out.
The build and the virtual environment need Python 3.11 or later (Ubuntu 22.04's system `python3` is 3.10: use a newer interpreter there).

The package is built as the ordinary user, from an export of the committed revision, and only the resulting wheel is installed as `root`.
Nothing is built as `root`, and nothing is written into the working repository: an uncommitted change cannot slip into the installation, and the checkout gets no `root`-owned build files.
Building lets `pip` fetch the build requirements (`setuptools`) unless they are already present; an offline build needs them provisioned in advance.
Installing the wheel needs no network: the package has no runtime dependencies.

[source,text]
----
$ build=$(mktemp -d)                                                   # as the ordinary user
$ git archive --format=tar --prefix=source/ HEAD | tar -x -C "$build"
$ python3 -m pip wheel --no-deps --wheel-dir "$build/wheel" "$build/source"
$ sudo install -m 0644 deploy/sysusers.d/aquaponics.conf /etc/sysusers.d/aquaponics.conf
$ sudo systemd-sysusers /etc/sysusers.d/aquaponics.conf
$ sudo python3 -m venv /opt/aquaponics/venv
$ sudo /opt/aquaponics/venv/bin/python -m pip install --no-index --no-deps "$build"/wheel/aquaponics_controller-*.whl
$ rm -r "$build"
$ sudo install -m 0644 deploy/systemd/aquaponics-engine.service /etc/systemd/system/aquaponics-engine.service
$ sudo systemctl daemon-reload
$ sudo systemctl start aquaponics-engine
----

`systemctl enable aquaponics-engine` makes it start at boot; do this only where boot start is wanted.
The runtime and state directories are created by systemd; do not create them by hand.

A deliberate stop (`ape -x`, `systemctl stop`, a handled `SIGTERM`) exits 0 and is never restarted.
A restart is never a sign of success: the reason is in the journal and, where the Engine could record it, in the lifecycle audit history.
An execution killed by a signal or the watchdog has no `SHUTDOWN_*` records; the next execution does not yet detect this (future work).

==== Readiness and Watchdog

The Engine reports to systemd through the notification socket (`NOTIFY_SOCKET`), from its main flow only: no thread and no timer.
Each report is one non-blocking send and is never retried, so reporting can never block the Engine.

`READY=1`:: Sent once, at the end of startup: after `ENGINE_RUNNING` is recorded and the IPC endpoint listens.
If it cannot be sent, startup fails (fail-stop): `ENGINE_FAILURE` with phase `startup`, cleanup, exit status 1, and systemd restarts the service within the start limit.
Without READY, systemd would end the start attempt after 30 s anyway.

`WATCHDOG=1`:: The heartbeat.
Sent only after an operating cycle has completed all its phases and been counted; never after a phase raised, never from the idle wait or idle-time request servicing, never after `STOPPING=1`.
At most once per quarter of the *actual* watchdog timeout (`WATCHDOG_USEC`, set by systemd from `WatchdogSec=10s`), so at most every 2.5 s.
A failed send is logged as a `WARNING` (repeat-suppression category `service-notify-failed`) and is otherwise ignored: if heartbeats really stop, the watchdog acts.

`STOPPING=1`:: Sent once at the start of every shutdown, whatever its reason. A failed send is logged and the shutdown continues.
If startup failed before the notification socket was opened (for example exit status 3, another Engine owns the endpoint), nothing is sent and nothing is logged about it: systemd learns the outcome from the exit status.

Activation:: Without `NOTIFY_SOCKET` (a terminal, the tests) nothing is sent and the Engine behaves exactly as before.
The watchdog is active only if `WATCHDOG_USEC` is also set and `WATCHDOG_PID` is unset or the Engine's own process ID; `WATCHDOG_PID` never disables READY or STOPPING.
A malformed variable is a configuration error (exit status 2).

Interval rule:: Cycle interval + 1.5 s (the worst-case cycle from the phase time limits) must be at most half the watchdog timeout.
Otherwise the Engine refuses to start (exit status 2).
With `WatchdogSec=10s` the cycle interval may be at most 3.5 s; the longest possible gap between heartbeats then stays below three quarters of the timeout.

Watchdog timeout:: systemd sends `SIGABRT`. With `PYTHONFAULTHANDLER=1` the Engine's Python stack (where it hung) is written to the journal (`Fatal Python error: Aborted`), and the service is restarted.

What the heartbeat means:: Only that the Engine's single control loop completed a full operating cycle recently.
It does *not* show that the administrative IPC is reachable, that any request was served, or that the physical installation is safe: six of the seven phases are still placeholders.
Once real control work exists, the heartbeat shall follow successful critical work (see "Meaningful Engine Heartbeat").
The systemd watchdog does not cover a frozen operating system; the Linux and hardware watchdogs are not configured (future work).

==== Journal

When standard error is the journald stream (`JOURNAL_STREAM` matches it), every line carries its syslog priority (`<3>` error, `<4>` warning, `<6>` info, `<7>` debug), tracebacks included; journald stores it as the entry's priority and removes the prefix.
Elsewhere the lines are unchanged.

[source,text]
----
$ journalctl -u aquaponics-engine -b                 # this boot
$ journalctl -u aquaponics-engine -p err             # failures only, with their tracebacks
$ journalctl -u aquaponics-engine -p warning -f      # warnings and worse, following
$ journalctl -u aquaponics-engine | grep 'exec=<id>' # one execution (see the lifecycle audit history)
----

Every Engine line carries the execution identifier (`exec=`), the same value as the lifecycle audit history, so executions before and after a restart can be told apart.
systemd adds its own lines about the unit (start, `Watchdog timeout`, `Main process exited, code=..., status=...`, `Scheduled restart job`).

The journal configuration belongs to the service setup, not to the Engine.
To keep the journal across reboots, set `Storage=persistent` in `/etc/systemd/journald.conf` (or create `/var/log/journal`) and bound it with `SystemMaxUse=`; record the result in the IT System Reproduction chapter ("Logging").
journald's rate limit (`RateLimitIntervalSec`, `RateLimitBurst`) can drop lines from a very noisy service; it then says so in the journal.

==== Troubleshooting

[cols="2,3",options="header"]
|===
|Symptom |Meaning and action

|"Start request repeated too quickly", the service stays failed
|More than 5 starts within 300 s (on systemd 249 `Result` keeps the last failure, for example `exit-code`; `NRestarts` counts the refused restart too). Find the cause in the journal first (`-p err`); then `systemctl reset-failed aquaponics-engine` and start it again. Resetting without understanding the cause only repeats the loop.

|`Watchdog timeout` in the journal, `status=6/ABRT`
|The Engine stopped completing operating cycles for 10 s (hung or frozen). The Python stack below `Fatal Python error: Aborted` shows where. Investigate; a watchdog shall not be used to hide a recurring failure.

|Exit status 2 at start
|Configuration error, for example a cycle interval too long for the watchdog. Not restarted. The journal line says what is wrong.

|Exit status 3 at start
|Another Engine owns the endpoint. Not restarted.

|`ape` exit status 3
|The service is not running (or is shutting down). Check `systemctl status`.

|`ape` exit status 4
|Not run as `root` or `aquaponics`.

|Inactive after `ape -x`
|Intended: an operator STOP is not undone. Start it again with `systemctl start`.
|===

==== Teardown

Removing or disabling the service *preserves persistent state*: the lifecycle audit history in `/var/lib/aquaponics/` is kept by default.

[source,text]
----
$ sudo systemctl disable --now aquaponics-engine     # or: systemctl stop, if it was never enabled
$ sudo rm /etc/systemd/system/aquaponics-engine.service
$ sudo systemctl daemon-reload
$ sudo systemctl reset-failed aquaponics-engine
$ sudo rm -r /opt/aquaponics/venv                    # optional: the virtual environment holds no state
----

* Runtime resources need no action: systemd removes `/run/aquaponics` when the service stops.
* `/var/lib/aquaponics/` and the audit records are *not* removed. Do not use `systemctl clean --what=state` or remove the directory as part of a teardown.
* Keep the `aquaponics` user (and `/etc/sysusers.d/aquaponics.conf`) while the state directory exists, so that the records keep their owner. A reinstallation finds and continues the same audit history.

Deleting persistent state is a separate, deliberate operator action, never part of a teardown.
It is permitted only on a non-production workstation, after confirming that the audit records are no longer needed, and preferably after archiving them (for example `sudo tar -C /var/lib -czf aquaponics-state-<date>.tar.gz aquaponics`).
Only then: `sudo rm -r /var/lib/aquaponics`, and, if wanted, remove the user (`sudo userdel aquaponics`, `sudo rm /etc/sysusers.d/aquaponics.conf`).

==== Validation

Three tiers (Issue #9, D16):

. *Deterministic tests*, always run (see "Running the Automated Tests"): the notification contract against a fake notification socket, the readiness failure path, the interval rule, heartbeats only after completed cycles, the `accept()` classification, journald priorities, and every contract directive of the unit, including `systemd-analyze verify` where it is available.
. *User-level systemd integration tests*, opt-in: `AQUAPONICS_SYSTEMD_TESTS=1 python -m pytest tests/test_systemd_integration.py`. They need a running systemd user manager (`systemctl --user`) and take a few minutes. Each test runs the Engine in a transient user unit (`systemd-run --user`, named `aquaponics-test-*`) built from the production unit: every behaviour directive is kept, only the identity and sandboxing directives are dropped. They cover READY and `ape --ping`; `ape -x` and `systemctl stop` not restarted; `SIGKILL`, `SIGHUP` and an Engine failure restarted, with a new execution on the same endpoint; exit statuses 2 and 3 not restarted; the start limit; a frozen and a hung Engine killed by the watchdog, with the Python stack in the journal; and execution identifiers and termination causes in the journal. Nothing is installed or enabled; teardown stops and resets each unit and removes its own directories.
+
*These tests do not validate* the production service identity (`aquaponics`), system-level sandboxing (including `PrivateDevices=yes`), start at boot, or Raspberry Pi behaviour.
. *Manual system-level demonstration*, below.

==== Manual System-Level Demonstration

On a non-production workstation with `sudo`, never on the live installation.

. Install as described in "Installation".
. `sudo systemctl start aquaponics-engine`; `systemctl status aquaponics-engine`; `sudo /opt/aquaponics/venv/bin/ape --ping --socket /run/aquaponics/engine.sock`.
. `sudo /opt/aquaponics/venv/bin/ape -x --socket /run/aquaponics/engine.sock`: the service is inactive and not restarted (`NRestarts=0`).
. Start it again. `sudo systemctl kill -s KILL aquaponics-engine`: restarted after 5 s with a new execution identifier. Then `-s HUP`: restarted. Then `-s STOP`: after 10 s the watchdog kills it and it is restarted.
. `sudo systemctl stop aquaponics-engine`: graceful, exit status 0.
. `journalctl -u aquaponics-engine -p err` and `systemd-analyze security aquaponics-engine` (the exposure score and every unmet restriction are worth recording).
. Check the audit history: `sudo tail /var/lib/aquaponics/lifecycle_audit.jsonl` shows each execution; those ended by a signal or the watchdog have no `SHUTDOWN_*` records.
. Tear down as described in "Teardown", which keeps `/var/lib/aquaponics/`.

==== Known Limitations

* *IPC availability is not part of the heartbeat.* Two cases leave the Engine running, and sending heartbeats, while administrative access is unavailable: persistent descriptor or memory exhaustion (contained and rate-limited by design), and the socket path removed from outside the Engine. `systemctl stop` and `restart` still work. Treating IPC availability as part of Engine health is a separate issue.
* The heartbeat does not show physical safety (see "What the heartbeat means").
* Synchronous diagnostic logging can block (see "Diagnostic Logging (Initial Implementation)"); a journald stall longer than the watchdog timeout ends in a watchdog restart.
* An unclean previous execution is not detected at startup; failure notifications (`OnFailure=`) are not configured; restarts use a fixed 5 s delay (graduated backoff needs systemd 254 or later).
* The Linux and hardware watchdogs are not configured; the API service does not exist yet.
* Verified on systemd 249 (Ubuntu 22.04) with user-level units. Raspberry Pi OS (bookworm, systemd 252) is the target but has not been verified on the controller hardware.

=== Meaningful Engine Heartbeat

A running Python process is not sufficient proof of a functioning Engine.

The Engine heartbeat should demonstrate that meaningful control work is progressing.

A heartbeat should only be refreshed after completion of an appropriate healthy control-cycle milestone.

Conceptually:

[source,text]
----
control cycle progresses
        |
        v
critical work succeeds
        |
        v
heartbeat refreshed
----

A deadlocked but still-existing process shall eventually be detectable as unhealthy.

Initial implementation: the systemd watchdog heartbeat is sent after each completed operating cycle (see "Readiness and Watchdog" under "Engine Service (Initial Implementation)").
It detects a hung or frozen Engine, but while the operating cycle performs no real control work it shows only that the control loop progresses, not that critical work succeeds.

Production should preserve enough local diagnostics to distinguish:

* Engine crash;
* Engine hang;
* API crash;
* IPC failure;
* OOM;
* storage failure;
* DB failure;
* kernel problem;
* watchdog reset;
* clean reboot;
* unexpected reboot;
* power loss;
* repeated restart;
* command backlog.

Important diagnostic information should survive reboot where practical.


=== Logging Operations

Production logs shall be:

* bounded;
* rotated;
* locally available;
* sufficiently detailed for diagnosis;
* separated from durable domain history where appropriate.

Logging failure shall not normally terminate core physical control unless it indicates a wider storage failure requiring safe degradation.

Writing a log record shall not block physical control for an unbounded time.
The initial implementation does not yet meet this: its logging is synchronous (see "Diagnostic Logging (Initial Implementation)"), which must be resolved before physical equipment control is enabled.

Sensitive information shall not be written unnecessarily to logs.


=== Production Database

The authoritative operational database shall be local to the production controller.

An embedded database such as SQLite is an appropriate initial implementation.

A remote DB server shall not be required for physical control.

This prevents failure of:

* LAN cable;
* Ethernet switch;
* another computer;
* remote database service;
* Internet connection;

from stopping the aquaponics controller.


=== Database Access Ownership

Normal operational database access belongs to the Engine.

The API shall not require direct database-write access.

Normal API and CLI queries shall use supported Engine query semantics rather than coupling themselves to private SQLite schema.

This preserves:

* schema independence;
* Engine authority;
* validation;
* migration freedom;
* access control.


=== Command Journal Operations

The Engine may use the production database as its durable command journal.

Operational procedures shall therefore consider command state during:

* startup;
* shutdown;
* backup;
* migration;
* restore;
* failure recovery.

Backup and restore procedures shall preserve enough information to reconcile accepted but incomplete work safely.


=== Backup Operations

Backups shall not interfere with core control.

Loss of the backup destination shall not stop the Engine.

Backup procedures shall define:

* frequency;
* retention;
* consistency method;
* destination;
* restore procedure.

A backup process is not considered proven until restoration has been tested.

SQLite backups shall use a transactionally safe mechanism.

A live copy of a database file during active writes shall not automatically be assumed consistent.


=== Local and Independent Backups

A copy stored on the same physical storage device is useful for some recovery scenarios but is not sufficient disaster protection.

The eventual backup model should conceptually support:

[source,text]
----
Live database
     |
     +--> rotating local backup
     |
     +--> independent off-device backup
----

Loss of off-device backup connectivity shall not affect physical operation.
